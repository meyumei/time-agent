# T4.5 记账迁移与账目合并、拆分

日期：2026-11-04。分支：`codex/t4.5-ledger`，开发基线：`e553670`。

## 本轮范围与规则

受影响账本：L10（支付记账）、L34（数据库迁移与备份）；导航与主题沿用已有实现。

用户明确要求支付账目本身支持合并、拆分，并在提出以下规则后回复“继续”，本轮按这些规则实施：

- 至少两笔同账户、同币种、同方向的账目可合并；确认页选择结果的分类、商户、备注与发生时间，金额为只读合计。
- 一笔账目可拆为至少两项；每项金额为正整数分，合计必须恰好等于原金额。每项选择分类、商户和备注，沿用原账户、币种、方向、发生时间。
- 原账目软删除；原支付草稿与交易号保留。多来源合并以及合并后再次拆分都保留全部来源关联。
- 合并、拆分分别是一条 CommandExecutor 命令，在同一事务内检查所见版本、保存结果和来源、删除原行，并形成一个撤销单元。相同 requestId 重试返回首次结果。
- 界面失败时保留草稿；冲突不自动换成最新版本重提。删除、合并、拆分提供 8 秒撤销提示；顶部撤销、重做仍保留。
- 合并、拆分可继承原账目的已归档分类；选择其他分类时仍须使用可用且方向相符的分类。已有历史账目的账户保留原币种，另一币种使用新账户，避免把旧金额改成另一单位。

## 实现

账本 UI 从 LedgerActivity 抽为 LedgerScreen，接入主导航。旧 Activity 保留支付通知深链和启动前数据恢复入口。今天页与管家页显示待确认数量，读取失败显示原因，再次打开账本时重试数量查询。

MoneyAmountField 使用数字小数键盘，输入阶段保留中间文本，失焦后将有效整数分格式化为两位小数。金额解析和加总不使用浮点；合并、拆分用精确整数加法检测超限。

支付捕获默认关闭。开启本地捕获或前往系统通知使用权设置前，先说明微信/支付宝支付通知的本机解析、草稿确认与不直接入账行为。原 CSV 导入、手工录入、账户分类、删除/归档和通知深链均保留。

## 数据库与备份

迁移前通过现有 PersonalBackup 创建本地快照。Room schema 15 由构建生成。备份表清单覆盖新表；v15 以前的备份按原版本校验，新表由既有兼容路径补为空表。

新增 MigrationTestHelper 真机测试源，覆盖旧账目保留、索引、外键与多对多约束。已有 BusinessMigrationTest 的最新版本预期同步为 15，没有删除旧数据保持断言。按用户安排，本轮不运行主机单测或逐任务真机回归。

后续尚未实施的数据库版本顺延：T5.1 v16、T5.2 v17、T5.4 v18、T5.6 v19、T5.8 v20、T5.9 v21。规格 06、08 已同步；这些功能尚未因此实现。

## 阶段 5 后集中真机验收清单

1. 在隔离测试包中准备两笔同账户支出 12.34 元、5.66 元，分别带不同支付来源和交易号；合并结果应为 18.00 元，旧行退出统计，两个来源完整显示。
2. 将 18.00 元拆为 10.00 元、8.00 元；总额仍为 18.00 元，两项都可追溯到原支付来源。追加分项、金额不等或非正数时不能提交。
3. 分别撤销、重做拆分和合并；确认结果行、原行、来源与总额一起恢复。重复提交相同 requestId 不产生新账目。
4. 打开确认页后从另一入口修改一笔原账目，再提交旧草稿；应提示冲突，所有账目与来源均不部分写入。
5. 导出 CSV，核对旧列顺序不变，金额为两位小数，来源和交易号列保留全部关联值；旧账目的单来源仍可导出。
6. 待确认数量在今天页、管家页一致；确认或忽略后更新。账本中的手工记账、CSV 导入、账户分类、删除归档、通知深链均走查。
7. 通知捕获默认关闭；取消说明不打开捕获；关闭捕获时微信/支付宝通知不产生新草稿；拒绝系统权限时提示正确。
8. 执行 v12/v14 → v15 MigrationTestHelper 用例及升级、旧备份恢复和新表备份往返。仅在完成正式应用数据备份与隔离验收后覆盖安装；保留手机原记录、系统字号和正式包。

## 限制与回滚

本轮尚无上述真机验收结果，不宣称 L10/L34 已全项通过，不操作手机数据。个人备份、原始通知、真实账目、密钥和完整 DS 原始日志不提交仓库。

旧版本若曾更改有账目账户的币种，原账目没有单独保存当时币种，不能可靠重建历史货币单位。本轮阻止继续发生这种重解释，不推测或批量改写旧金额。

v15 已写入后不能直接用 v14 APK 降级打开。回滚应使用迁移前快照，在确认恢复路径后恢复原版本数据；本轮未在用户正式数据上演练此过程。
