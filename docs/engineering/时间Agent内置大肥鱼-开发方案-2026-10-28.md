## 1. 最终产品与首版目标

用户安装时间 Agent 后即可使用时间管理和大肥鱼，无需另装、另开 DSHA，也不依赖电脑常开。鱼的运行环境放在时间 Agent 内部；推理按用户配置连接模型服务。

界面保持原生 Android：

**今天 / 计划 / 中央语音与自然语言输入 / 复盘 / 管家。**

鱼在 App 内能持续交流、记住共同经历、理解真实日程，并通过已适配的平台插件自主活动。外部见闻以闲聊带回同一角色的对话；人格、语气、性格、形象与动画由用户后续提供。

交付分成两档：

| 交付档次 | 必须做到什么 | 不能混淆的边界 |
|---|---|---|
| 第一份原型 APK | App 内启动运行时；原生输入发出一句话；鱼调用真实日程查询并回答；重新进入能接回会话 | 这是接线验证，不是完整养鱼版 |
| 首个可用版 | 四个主页与重点子页面重构；中央语音和文字可用；持久会话和共同记忆；主动话题；App 与 B站的一条真实见闻分享链路 | QQ、抖音、小黑盒不因界面出现入口就算完成接入 |

首个可用版优先完成 **App + B站** 两个场景的同一角色。QQ 随后按手机协议端可用性加入；抖音、小黑盒按后续找到的手机兼容插件扩展。

## 3. 目标结构与模块分工

下列模块名是拟定名称，不表示当前已经存在。

```text
时间 Agent APK
  |
  +-- :app
  |    +-- 四个原生主页与各业务子页面
  |    +-- 中央语音 / 文字输入
  |    +-- FishChat：原生长期对话与角色呈现
  |    +-- TimeTools：复用现有 Repository 的业务能力
  |
  +-- :agent-runtime（新增）
  |    +-- 从 DSHA 抽取的必要环境和进程管理代码
  |    +-- DSH 运行环境与版本固定的所选插件
  |    +-- 运行状态、启动、停止、重新连接
  |
  +-- agent-plugins/time-agent（新增 DSH 适配插件）
  |    +-- 将原生输入交给 DSH 中同一角色
  |    +-- 回传文本、工具过程与会话历史
  |    +-- 将日程、任务、项目等工具请求送回 :app
  |
  +-- :core（沿用）
       +-- 现有时间与排程业务逻辑
```

### 连接方式

计划采用**本机回环上的双向连接**，优先以一条 WebSocket 承载会话输入、回复事件和工具结果。这个接口由本项目拥有，DSH 插件负责连接宿主的实际会话服务。

第一阶段必须用实际 DSH 服务验证 `发送消息 → 产生回复 → 调用日程工具 → 返回结果`。目前没有将“原生客户端接口已经现成”作为计划前提；也不根据 DSHA 使用 Web UI 就认定原生 UI 无法实现。

适配插件是接口桥，不另建一套人格、记忆或自主规则引擎。普通用户使用原生页面；DSH 的维护界面仅按开发与插件配置需要保留内部入口。

### 最小接口范围

| 接口组 | 首批能力 | 实际落点 |
|---|---|---|
| 运行模块 | 启动、停止、读取当前状态、重新连接 | `:agent-runtime` |
| 会话 | 发送文字、接收回复事件、读取历史、取消本轮回复 | DSH 会话服务，经适配插件连接 |
| 时间查询 | 今日摘要、某日安排、待办、项目概况 | 现有 Repository 与本地查询逻辑 |
| 时间操作 | 记录时间、创建任务、安排时间、完成任务 | 沿用现有 command/planner/writer |
| 平台事件 | 发现内容、参与讨论、分享给主人 | 所选平台插件 → 同一角色的见闻与消息 |

## 4. DSHA 源码取材范围

| 部分 | 起步处理 |
|---|---|
| `ContainerRuntime`、`RuntimeLauncher`、`ProotBootstrap` | 研究传递依赖，抽入运行模块，适配本 App 的目录和包名 |
| `HarnessService`、`HarnessController`、`WebProcessManager` | 提取启动和进程管理所需部分，由本 App 管理 |
| `WebLaunchCommand`、`DshAuthUrl`、`WebOutputSession` | 借用运行时启动和状态识别逻辑，接到项目内部接口 |
| DSH 与基础运行资产 | 先形成可运行的固定组合，再按实际插件依赖裁剪 |
| 插件安装管理 | 首期围绕固定的鱼插件组合，保留更换和升级所需的最小能力 |
| 人格、记忆、主动话题 | 选用一套主实现，不叠加多套记忆或心跳插件 |
| 完整终端、局域网网页、虚拟屏、ADB 工作台、独立更新页面 | 不作为首版产品功能；抽取时只保留实际必需的底层依赖 |
| Windows/SnowLuma/桌面组件 | 不直接作为手机运行依赖搬入 |

DSHA 自有代码按 MIT 复用并保留声明；运行资产按其实际来源处理。代码取材清单应记录来源版本、源文件、保留原因和具体改动，便于后续维护。

内部运行原型先以 `arm64-v8a` 手机为目标，符合本轮研究到的 DSHA 运行环境。现有业务 App 的其他架构支持不等于内置鱼已支持这些架构；具体 APK 打包方式在 P0 的资产清单中确定。

不以当前 DSHA 整包体积推算裁剪后的 APK，也不预先承诺大幅缩包。先得到一套真实可运行的最小组合。

## 5. 人格、记忆、会话和业务数据的归属

| 内容 | 主要保存位置 | 使用方式 |
|---|---|---|
| 用户角色设定、称呼、语气、形象引用 | 同一角色的配置 | App 和外部平台读取同一角色 |
| 长期经历、共同话题、主动目的 | 所选鱼插件的数据目录 | 沿用该插件的持久化与召回实现 |
| 完整对话回合和工具过程 | DSH 的持久会话 | App 读取同一会话历史，UI 状态只是显示投影 |
| 日程、任务、实际记录、项目、健康训练 | 现有业务数据库与 Repository | 鱼按需要查询和操作，统计回到原始记录 |
| App 的导航和输入草稿 | 原生 UI 层 | 不影响角色身份 |

每条鱼使用稳定的角色标识。各平台可以有不同会话，但使用共同角色与按来源记录的经历；不强行把所有群聊、平台上下文合成一个原始会话。

个人记忆中已有的排程约定仍由现有业务能力使用；鱼的社交经历通过所选记忆实现延续。具体需要的互通由适配插件完成，避免将同一事实维护为两份互相竞争的业务记录。

本轮不指定新的 Room 版本。是否需要新增表，由会话和业务接口的实际存储需求决定；新旧数据的升级安排随对应实现一起交付。

## 6. 页面与输入开发范围

### 导航与主页

| 页面 | 首屏重点 | 主要内容 |
|---|---|---|
| 今天 | 当前事项、下一步 | 时间轴、今日待办、临近期限、计时、补记、开始训练 |
| 计划 | 组织未来 | 项目任务、周期习惯、生活期限、周目标、收件箱 |
| 复盘 | 本周进展与实际投入 | 项目进度、时间趋势、健康训练、可回看的明细 |
| 管家 | 同一条鱼及长期交流 | 原生聊天、共同记忆、平台连接、养鱼互动、设置 |

中央按钮始终是语音与自然语言快捷入口。保留按住说话、实时文字、上滑取消和键盘输入；底栏仍是四个目的地加一个中央动作。

中央输入和管家完整聊天指向同一条鱼。中央输入方便同页办事，管家页承载长对话。明确的本地记录可沿用快捷路径，执行结果也呈现在该角色的交流中。

### 优先重构的子页面

1. 项目：项目列表 → 详情 → 下一项任务 → 排进今天 → 执行 → 看进展。
2. 周期：本次实例 → 完成或调整本次 → 查看规则与以后安排。
3. 生活期限：按日期分组 → 详情 → 处理或延期 → 返回分组。

同时统一标题、列表、详情、编辑、筛选与返回方式；再应用到收件箱、健康训练、历史与设置。

角色素材暂缺时使用明确占位。布局、会话连接和业务工具可以先交付，口吻、立绘、动画和具体养鱼玩法在用户提供素材后补入。

## 7. 开发阶段与交付顺序

### P0：锁定取材与做出原型 APK

**这是第一项实施任务，与页面线框并行。**

先由主代理完成一页接口勘察结论，确认 DSH 实际的会话入口、历史读取与插件向 App 回调工具的路径，再固定运行模块与插件之间的接口。来源版本、插件组合与共享接口由主代理决定后下发。

P0 分两段交付：**P0a 原生输入连接真实 DSH 会话；P0b 同一会话查询真实日程并恢复历史。** P0a 完成可以交付阶段原型，P0b 做通后才算整个 P0 完成；不以固定回声或独立模型回复代替真实会话。

工作：

- 固定 DSHA 来源、DSH 版本和一套拟用鱼插件的具体仓库与版本。
- 建立取材清单与内部运行模块，接通实际 DSH 会话。
- 用原生文字输入发一句话，再让同一回合调用 `今日安排` 查询。
- 先沿用现有 App 界面，角色设定使用临时占位配置。
- 在原生界面显示首次运行环境准备进度，并提供重新尝试当前准备步骤的入口。
- 将新增模块、插件与运行资产纳入现有验证副本的同步和打包入口。

现有验证脚本只固定同步部分源码路径。P0 要明确补齐新增模块、插件来源、运行资产与必要 native 库的实际路径，避免只构建到旧副本。

交付：一份原型 APK、一张实际连接图、固定的来源与版本清单。

完成表现：无需独立 DSHA App 或电脑；输入能到达真实运行时；回答使用 App 内真实日程；再次进入可接回该会话。原生界面到 DSH 的连接若未做通，就不能将本阶段标记完成，也不替换目标为一个独立聊天模型。

### P1：原生页面结构重构

工作先分成两批：P1a 完成今天、计划、项目流程与中央输入外壳；P1b 沿用同一组件扩展复盘、管家、周期任务和生活期限。四个主页的线框先一并确定，页面逐批实现。

共享导航与组件由主代理先定。P1 不另做 FishChat 会话数据层，该部分在 P2 接入已经验证的真实接口。

交付：页面原型、导航与功能归属图、可运行的原生页面 APK。

完成表现：安排任务、补记时间、调整本次习惯、处理期限、整理想法、开始训练六件事有清楚入口和返回路径；已有功能能找到。

依赖：线框可在 P0 同时完成；页面实现使用约定的接口，不等待人格形象。

### P2：同一条鱼的持久交流与业务工具

工作：将中央语音和完整聊天接到同一角色；读取持久历史；接入日程查询、待办与项目，再连接记录和安排等现有业务写入能力。

交付：可持续使用的内部鱼会话，语音、文字与工具过程演示。

完成表现：用户在中央说完，进入管家页能继续同一话题；关闭再进入仍能读到历史；在对话中安排的任务能在今天和项目中找到。

### P3：共同记忆、主动话题与持续运行

工作：接入选定的记忆与主动插件、原有运行服务管理；将 App 中的真实经历作为必要的话题来源。复用插件既有机制，不新做自主规则平台。

分开交付：P3a 在正常使用中验证记忆延续；P3b 接主动话题，在前台或短时后台先体验；P3c 记录较长时段的后台持续运行情况。P3a/P3b 可以先完成，不以全时段后台体验结束为前置。

交付：共同记忆、主动话题、后台运行与重新进入的实际体验记录。

完成表现：能承接先前话题；主动消息来自真实经历；界面退出和重新进入后角色、历史与记忆延续。报告实际后台运行情况，不把“存在前台服务”当作全天运行证明。

### P4：B站见闻与同一角色回流

工作：选一个手机兼容的 B站能力插件；接内容发现、评论或动态等已支持能力；将经历交回共同记忆，由鱼自然开启或继续话题。

交付：App + B站的完整演示，标明实际已支持的动作。

完成表现：鱼发现真实内容 → 在 App 内自然提起 → 用户追问 → 鱼继续交流；来源能打开；角色识别保持一致。评论与动态沿用所选插件的自主方式。上传视频作品只有找到并接通对应能力后才计入交付。

### P5：可用版收尾与角色呈现

工作：串起页面、中央输入、持久交流和平台回流；补入用户提供的人格与形象，完善鱼在不同页面的表现。

交付：首个可用版 APK、简明使用说明、功能与真机演示记录。

角色素材尚未提供时，可以使用占位完成技术体验版；不会代写最终人格，也不因此阻塞其他阶段。

随后扩展：QQ、抖音、小黑盒、更多养鱼互动。每个平台接入同一角色，不分别生成独立的鱼。

## 8. 主代理与 DS 4.1 的开发分工

计划中的子任务继续通过 WorkBuddy CLI 使用 DS 4.1。实际模型以返回记录为准，按任务规模选择 effort。以下是后续实施时的所有权分配，本轮尚未下发开发任务。

| 工作包 | 主要负责者 | 所有权与边界 |
|---|---|---|
| 来源、插件组合、取材范围与接口勘察 | 主代理 | 先确定版本与边界，形成任务输入 |
| 运行模块 | DS 4.1 A | `agent-runtime/` 内部实现；使用主代理已定来源与公共接口 |
| DSH 适配插件与会话事件 | DS 4.1 B | `agent-plugins/time-agent/`；不直接修改业务数据库 |
| 页面结构、导航与共享组件 | 主代理 | 先提供共享规则，不按页面分给多人同时修改 |
| 独立页面实现 | DS 4.1 页面任务 | 指定具体 UI 文件，沿用组件与导航；不修改 FishChat 数据层 |
| 原生接入、工具映射与全局整合 | 主代理 | `TimeViewModel`、`TimeAgentApp`、中央输入、Repository 接入与共享入口 |
| 模块注册、Manifest、构建脚本、必要的数据变更 | 主代理 | 统一修改共享文件，避免多方同时写 |
| B站插件手机适配 | DS 4.1 专项任务 | 选定的平台目录，使用已定角色和事件接口 |

开始时最多并行两个独立工作包：运行原型与页面线框。会话桥依赖运行接口先确定，平台适配依赖角色与记忆链先打通。

每个任务说明输入、所属文件、共享接口、要展示的真实行为和结束条件。子代理只负责自己的工作包，不回退其他人的修改；主代理负责整合和实际交付判断。

## 9. 验收如何贴近实际使用

每阶段只验证本阶段行为和受影响的现有能力。关键演示包括：

1. 新设备只安装时间 Agent 即可进入内置鱼；运行环境准备进度可见。
2. 中央语音与文字均能送达同一角色，管家页能接着聊。
3. 查询真实日程；在对话中安排一次任务后，在业务页面找到结果。
4. 关闭并重新进入后，同一角色、历史与记忆仍可继续。
5. B站真实内容带回自然交流，追问有连续上下文。
6. 原有任务、记录、习惯、训练与健康页面仍能使用。

源码与接口有针对性的测试；APK交付沿用现有构建入口，完成必要的 core/app 测试、组装和 Lint。新增运行模块与资产必须实际进入验证副本和 APK。页面通过手机截图和六条真实使用流程查看。

这部分用于判断功能是否做成，不另立通用审批系统、审计平台、无限故障注入或新的规则引擎。

## 10. 第一轮开发任务单

按以下顺序发起：

1. **运行原型任务**：固定来源与插件 → 内部启动 → 原生文字发消息 → 真实日程工具回复 → 再次进入读回会话 → 输出原型 APK。
2. **页面设计任务（可并行）**：四个主页与中央输入 → 三组重点子页面 → 六个日常操作走通。
3. **接通任务**：将既有语音、工具与 P0 会话桥结合，形成原生完整对话。

第一轮做到这些，再进入共同记忆、主动活动和外部平台。其余阶段按实际完成情况推进，不要求用户每阶段重复批准已确定的开发方向。

## 11. 已明确的依据与待落定项

已明确：独立 App 是产品目标；DSHA 自有代码可按 MIT 借用；DSH 与插件依赖保留；原生中央输入和页面保留；多平台共用角色；没有完整观看三个视频，既有研究以原始仓库资料为主。

P0 必须落定的三项：所选鱼插件的具体版本、原生会话接口的实际接法、所选组合需要保留的运行资产。它们是起步任务的产出，不应在后续开发中一直作为泛化的 TODO。
