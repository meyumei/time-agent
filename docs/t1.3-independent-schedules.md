## 行为与数据变更

- 主库从 v12 升至 v13，重建 `schedule_blocks`，保留全部旧列、旧行及 `taskId`/`startAt` 索引。`taskId` 允许空值，外键继续为 `ON DELETE RESTRICT`；新增日程标题、类型、全天日期、创建时区、备注、颜色、来源、来源引用和软删除字段。新增 `command_log`，以 `requestId` 为主键；本轮只交付表与 DAO，不声称已有 CommandExecutor 幂等协议。
- 独立日程直接保存日程，不隐式创建任务或实际记录；有关联时标题可回退到任务标题。原有“新建任务并安排”和“关联已有任务”入口保留，网格编辑器增加“独立日程”。普通编辑器支持独立标题、备注及可选关联。
- `POINT` 保存 `endAt == startAt`，不计入时长、空闲占用和冲突；时间轴内部沿用要求正时长的 `TimeSpan`，只使用 1ms 显示锚。编辑器从原实体读取并保存，实测不会把显示锚写回数据库。
- `ALL_DAY` 保存包含结束日的 ISO 日期，以创建时区的开始日零点至结束日次日零点归一化；跨夏令时不按固定 24 小时计算。纽约 2026-10-31 至 2026-11-01 的两天全天日程实测为 49 小时。
- 删除有关联日程的任务时，必须选择“同时删除关联日程”或“保留为独立日程”。保留时补入原任务标题，已有独立标题优先；任务与日程作为一次操作撤销/重做。日程自身删除改为软删除。
- DAO、助手创建/查询/移动/取消、鱼工具、简报、项目复盘、建议、回复副驾、周期事务和时间轴均适配空 `taskId`、标题、软删除与 `POINT`。旧版 PLAN JSON 操作历史缺少新字段时补默认值，保留旧撤销/重做能力。

## 迁移前快照与恢复边界

生产数据库唯一注册的是 `ScheduleMigration.withBackup(context)`：在 Room 原库迁移事务内先调用 `PersonalBackup.createBeforeMigration()`，快照成功后才执行重建 DDL。直接使用原生 SQL 句柄，避免迁移过程中重新进入主库 Room/Hilt 单例。

快照沿用 format1，包含主库、训练库、附件、自定义内容与公开设置，排除 API Key。已有训练库使用独立连接与事务捕获，不写业务行；训练库尚不存在时记录正确的空 v1 数据，不创建训练 Room 单例。各库分别保持一致快照，不宣称两个数据库之间具有原子快照。

文件位于应用的 `noBackupFilesDir/migration-snapshots/v12-before-v13-<时间>-<UUID>.json`，使用 `AtomicFile` 写入，正常情况下保留最新两份。旧快照清理失败不会让已经生成有效快照的升级失败。快照写入失败则中止迁移，原 v12 表、数据和索引保持，且不留下新表或 `command_log`。

v7–v12 的 format1 备份恢复至当前 v13 时，旧日程补入新字段默认值，`command_log` 为空；v13 自身备份包含该表。若较早版本一次连续升级，快照表示进入 12→13 前的逻辑 v12 数据边界，不是原始低版本数据库文件副本。

本轮验证的是**把备份数据恢复进当前 v13**，并非降级 APK 或把 schema 降回 v12。format1 原有 32MiB、单元格和附件大小等限制继续存在；Linux/DSH 完整备份与备份 v2 仍属 T6。发布前仍须完成设备上的迁移与恢复验证。
