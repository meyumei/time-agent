# T1.4：CommandExecutor

日期：2026-11-02。分支：`codex/t1.4-command-executor`，基于 T1.3 提交 `c8b1c83f82c0413963b18de0219d7b05b265068c`；PR 叠在 `codex/t1.3-independent-schedules` 上，不合并 main。

本任务按规格 08 章 §3 的 T1.4、06 章 §4 实现统一命令入口。数据库继续使用 v13，没有新增表、字段或 Migration；冻结的 v12 夹具不变。最终自动回归结果见下文，设备验收仍待执行，PR 保持 Draft。

## 变更与调用范围

- 新增 `domain/command/Command.kt`、`CommandResult.kt`、`CommandExecutor.kt`。命令包含 requestId 与 Origin；结果包含 APPLIED / DUPLICATE / CONFLICT / INVALID / NOT_FOUND / FAILED、受影响实体与新版本、撤销 token、人类可读消息和版本冲突当前值。
- 第一批命令为日程及实际记录的创建、修改、删除，计时开始/停止/切换，以及批量、撤销和重做。修改/删除命令必须携带 expectedVersion；创建同 ID 已存在时不覆盖。
- 现有 Repository 的对应公开方法转为兼容入口，统一构造命令；旧调用方的参数、返回类型、冲突提示、未来实际确认和计时切换确认保留。旧调用方未传 expectedVersion 时，在同一个事务中捕获当前版本；类型化修改/删除命令则要求显式传版本。
- 时间轴编辑会话使用稳定的 `editor:<会话ID>`，删除确认保留同一请求号，停止计时请求号由记录 ID 与版本构成；删除与停止传入界面选中的版本。页面布局、导航和可见操作没有重做。
- Hilt 提供单例 CommandExecutor，和同一 Repository 的 `commands` 是同一个对象；EntryPoint 同样返回该实例。

T1.4 的“先迁移”范围不等于已经统一全部业务模块。鱼工具 toolCallId、本地解析/任务写入及通知按钮的完整协议转换仍为 T1.5；健康导入、课表导入、记账/整理、训练状态及其他模块仍保留其现有模块事务与日志，不能将本任务结果写作“全 App 所有写入已迁移”。这些模块调用本次已转换的 Repository 日程/记录/计时接口时，会经过执行器。

## 幂等、版本与返回值

一个成功命令在同一 Room 事务中保存业务变更、既有 OperationEntity 撤销组和 `command_log` 结果。相同 requestId 再提交，从持久日志返回首次结果，仅将状态改为 DUPLICATE；不再改实体、版本或操作历史，也不重复发事件。即使请求体后来变化，首次结果仍优先；撤销后重试原请求不会复活原写入。

版本不符返回 CONFLICT，附 expectedVersion、currentVersion 和当前实体 JSON；找不到目标返回 NOT_FOUND，内容不合法返回 INVALID。拒绝和失败不留下业务写入、版本增量、历史或命令日志，允许修正未成功的请求后再提交。保存命令日志失败同样回滚此前业务与历史写入。公开命令入口将非预期异常转为 FAILED；旧 Repository 兼容入口经同一个执行流程保留原数据库异常类型，让既有创建和训练回记流程继续按原语义处理失败。

既有日程冲突仍可保存并返回 warnings，不误当版本拒绝。实际记录仍允许重叠。POINT/全天和独立日程的规则沿用 T1.3；周期模块对同一日程 ID 的重复删除、使用当前版本重新排程仍可用。

计时兼容接口需要返回实体，因此成功结果额外保存 `timerRecord` 快照。后续记录被编辑或删除时，原请求重试仍返回首次计时结果，不依赖当前行存在，也不重新写回该行。API Key、鱼聊天和共同记忆不进入这些命令结果。

日志保留 30 天，按成功写入触发清理，删除严格早于“当前时刻减 30 天”的结果；恰好 30 天的记录保留。本轮没有另加周期清理任务。撤销历史不随命令结果清理。

## 事务、撤销与事件

`BatchCommand` 的子项为本批的变更步骤，整批只有一个命令日志与一个撤销组；子项不单独产生幂等日志。任一子项失败，前面子项、版本和历史全部回滚。

执行器复用现有 before/after 日志和 ASSISTANT_BATCH 撤销结构。嵌套在既有助手操作中的写入并入其原撤销组，token 指向父组；不拆出多份互相覆盖的撤销历史。计时切换中的“结束原计时＋开始新计时”同样是一组。UndoCommand 与 RedoCommand 保留原 LIFO 和 redo 分支语义，旧 token 不能撤销无关的新操作；版本仍单调增加。

DataChanged 使用进程内 SharedFlow。事务内只排队；外层 Room 事务实际成功后才发布受影响类型。重复请求和回滚不发布。嵌套事务失败会将共享事务标记为 rollbackOnly；即使外层捕获了内部拒绝结果，外层也不能按成功路径结束或发布已回滚内容的事件。事件是本轮新增接口，未来的小组件、日历和统一提醒消费者仍按各自任务接入。

业务执行保留调用方的取消能力；只保护 Room 提交及返回的窗口。成功提交后，即使调用方此刻取消，也在释放 PersonalDataGate 后完成一次事件发布。提交前取消则回滚，不留日志、不发事件。测试用真实 SQLite 委托包装器在最外层 `endTransaction()` 完成后取消调用方，没有新增生产测试开关。

## 测试与审查

先写测试，再确认缺少命令类型的编译红灯；随后以最小空执行器运行，16 项测试中 14 项失败，观察到 APPLIED/CONFLICT/INVALID 等预期与实际 FAILED 的差异。两个已通过项目仅证明空实现没有写入，不冒充完整红灯。

新增的命令与兼容入口测试覆盖：

- 重新创建 Repository/执行器后重复提交仍返回首次结果；撤销后重试不复活数据。
- 版本冲突、重复实体 ID、非法内容、目标不存在，不留数据、日志、历史或版本残留。
- 两协程提交同一请求只写一次；两协程用相同旧版本编辑时只有一个成功。
- 批量只产生一个撤销组，任一子项失败全部回滚。
- 计时重复开始、切换整体撤销、重复停止保留首次结束时刻与版本。
- 实际记录 CRUD、重叠、删除后撤销，删除后请求重试及停止后记录被删的重试。
- 成功才清理超过 30 天的日志；日志 INSERT 失败整体回滚。
- 事件等待外层提交，外层失败及捕获内部拒绝后回滚均不发布，重复不再发布。
- SQLite 提交边界取消后实体/日志保留、事件仍恰好一次；提交前取消则整体回滚且不发事件。
- 既有周期同 ID 重排、助手一组撤销、原 warnings 返回与 Hilt 执行器单例。

本轮修复的五类可复现问题：

- 软删除日程被过早判为不存在，影响周期重复删除和同 ID 重排。
- 删除/停止重试在读取日志前依赖已消失的记录。
- 嵌套拒绝被外层捕获后误发回滚事件。
- 完整回归中 GridCreationTest 和 WorkoutRepositoryTest 两项失败：统一结果丢失旧入口的 SQLite 异常类型。保留原测试期待，修复兼容入口后定向回归通过。

首轮定向、transaction-red、retry-red、acceptance-regression 和 cancellation-red 的失败证据保留；修复后的 integration-green、legacy-exception-green、cancellation-green 均实际执行通过。既有业务测试不为迁就实现而删减。完整命令的最终结果另列，不把定向回归当作完整回归。
