## 真机测试发现并修复的问题

### Python 执行权限与自动修复（0.12.1）

上游 glibc Python 归档中主程序权限为 `0644`。原 DSHA 安装器会单独补执行位，本项目最初遗漏。手机实际表现为 Node 可以执行，Python 报 `'/usr/bin/python3.12' is not executable`。

0.12.1 安装逻辑补齐了可信运行文件的执行位修复：检查真实父目录、要求 Python 为普通文件，以 `O_NOFOLLOW` 打开文件描述符后修改权限；新安装及已发布运行目录均会检查，保留会话和记忆。

为验证自动修复，安装 0.12.1 前曾在应用运行目录恢复 Python 为 `0644` 并还原四份旧模块。之后从 App 正常启动，实际恢复为可执行并完成 RUN5 模型与工具测试。这一自动修复试验对应 **0.12.1**，不伪称在 0.12.2 上再次人为破坏并重做。

### 四份 DSH 模块依赖独立 DSHA 宿主（0.12.1）

复用运行资源中的四份 DSH 模块被 DSHA 修改，依赖其 `dsha-destructive-policy` 及独立宿主同意服务。本应用没有整套 DSHA 宿主，导致插件导入失败。

0.12.1 改用同版本 `0.2.1-rc.2` 的四份官方 npm 源文件，保留 Android / arm64 运行依赖。版本、npm integrity 和文件 SHA-256 已写入资源清单。0.12.2 启动后，主代理对手机实际四份模块逐项计算散列，仍与清单一致；手机中的 `host.mjs` 和 `protocol.mjs` 也与本次源码相同。

本原型禁用通用 Shell、文件读取/搜索和文件替换工具，业务工具继续走本应用既有 Repository / Planner / Writer。没有伪造 DSHA 同意服务或添加恒定放行的兼容桩。

### 模型请求失败未显示错误（0.12.2）

0.12.1 的 RUN4 曾出现真实 `DeepSeek Messages transport failed`，持久事件为 `turn/end.data.reason.kind='error'`、错误码 `TRANSPORT`。原 host 错误地检查 `kind==='failed'`，漏掉了真正失败，界面可能继续显示请求进行中。

0.12.2 在 `protocol.mjs` 中集中检查最后一个 `turn/end` 的 `reason.kind==='error'` 并抛出错误，host 复用原有 catch 发送 `turn_error`，由 Android 既有错误显示路径接收。

验证分为三层：

- 按真实日志形状先复现旧逻辑的漏报，修复后 Node 回归测试 3/3 通过。
- 用真实本地 DSH Harness、合成密钥及 localhost 的合成 401 验证，实际发出 `turn_error`，没有误发完成事件。
- 0.12.2 手机三次正常请求通过，且手机新 host/protocol 散列匹配。**没有对手机断网或改密钥注入故障，因此手机异常提示的强制复现仍未测。**

0.12.1 同时限制了长错误提示行数并避免管家页重复全局提示；异常态布局也没有在本轮手机上强制故障注入验收。
