## T1.2 SPEC review — findings

**1. Low — two independent wall-time sources drive the same UI (`ClockSource` vs `repository.now()`)**

`app/src/main/java/com/timeagent/ui/TimeViewModel.kt:57` builds `now` from `clock`, but the week anchor is built from the repository clock: `TimeViewModel.kt:58` (`_weekStart`), `TimeViewModel.kt:63-64` (`week` initial and `combine` input), `TimeViewModel.kt:96` (`currentWeek()`). The production binding is a *different* clock object (`app/src/main/java/com/timeagent/di/ClockModule.kt:17`, `Instant::now`), and `MainActivity.kt:43` passes it explicitly into a VM that also holds a `TimeRepository` with its own injectable `java.time.Clock`.

- Trigger: any `TimeViewModel` whose injected `ClockSource` and `repository` clock disagree — e.g. `MainActivity`'s Hilt clock together with `TimeRepository(db, fixedClock)` (the pattern already used at `app/src/test/java/com/timeagent/ui/ClockRecompositionTest.kt:105`).
- Impact: `week.today` and week paging follow the repository date while the timeline/briefing/review render the clock date, so `WeekHeader`/`currentWeek()` can land on a week that does not contain the day the timeline shows; the RunningTimerBar shows `Duration.between(record.startAt, now)` across two clocks, so elapsed time is offset by the clock delta.
- Scope: default production (both are system time) is consistent, so this is a consistency/trap issue, not a shipped-path failure. The added test cannot catch it because it constructs `TimeViewModel(repository)` (`ClockRecompositionTest.kt:110`) and therefore exercises the repository-bound fallback, never the Hilt singleton. Minimal fix: derive `_weekStart`/`currentWeek()` from `clock.now()` so all UI date math has one wall clock, leaving `repository.now()` for writes.
