## 一句话结论

原来的四个用户任务区域继续承载业务，FishButler 作为贯穿全 App 的管家层，DSH 只提供事件、插件、状态和审批的参考思想。

不要把“大肥鱼”做成第五个业务入口，也不要把养鱼游戏和任务、提醒、统计混在一起。

## 三层产品结构

```text
用户任务层
├── 今天执行
├── 计划组织
├── 复盘洞察
└── 管家与设置

FishButler 管家层
├── 输入理解
├── 事实查询
├── 方案预览
├── 确认与执行
├── 主动建议
├── 记忆解释
└── 真实工作状态表达

娱乐表达层
└── 独立养鱼：喂养、装扮、收集、成长
```

三层的职责不同：

- 用户任务层回答“我要去哪里完成事情”。
- FishButler 层回答“谁帮我理解、判断、执行和跟进”。
- 养鱼层回答“我和这条鱼如何相处和娱乐”。

## 一级导航怎么改

建议将当前“时间轴 / 任务 / 复盘 / 我的”调整为：

| 一级入口 | 作用 | FishButler 的结合方式 |
|---|---|---|
| 今天 | 今天要做什么、现在做什么 | 显示管家简报、主动候选、快速输入和当前工作状态 |
| 计划 | 管理未来和持续目标 | 管家可以把自然语言转成项目、任务、习惯或期限预览 |
| 复盘 | 看完成情况和趋势 | 管家解释异常、生成复盘草稿，但数字必须回到源记录 |
| 管家 | 管理人格、记忆、主动规则和养鱼 | 展示完整 FishButler 页面；设置作为二级内容 |

“管家”不等于“设置”。设置应成为管家页中的一个分组，不能继续用“我的”作为所有未分类功能的收纳箱。

## FishButler 在各页面的形态

### 今天页：完整入口

今天页顶部放一个可收起的 FishButler 状态卡：

- 鱼当前状态：空闲、倾听、思考、工作、等待确认、完成、错误、休息。
- 一句话简报：下一项任务、临近截止、空档、需要确认的事项。
- 一个主操作：继续处理当前事项或开始输入。
- 最多展示 1–3 条主动候选。

鱼的动画必须来自真实 `ButlerEvent`。没有事件时保持安静，不能随机播放“思考中”。

### 计划页：作为助手，不抢业务焦点

项目、子任务、周期任务、生活期限和收件箱仍然由普通列表、筛选、详情和编辑流程承载。

FishButler 只在这些位置出现：

- 快速新增入口。
- 自然语言转结构化任务的预览页。
- 冲突、重复、权限和风险提示。
- 用户主动请求拆分或安排时的辅助入口。

不要让鱼在每一条任务卡上都出现，否则它会变成装饰和视觉噪音。

### 复盘页：解释结果，不替代数据

FishButler 可以生成：

- “本周计划多、实际投入少”的解释草稿。
- 项目复盘提问。
- 下周目标建议。
- 需要用户确认的调整方案。

但所有数字、趋势和原始记录仍由时间 Agent 数据层提供。鱼只能解释和建议，不能修改统计口径。

### 管家页：完整状态中心

管家页分为四个区域：

1. **对话与输入**：文字、语音、当前会话和待处理方案。
2. **主动管家**：建议历史、安静时段、每日预算、冷却和静默记录。
3. **记忆**：稳定画像、带时间经历、当前工作状态、来源和召回审计。
4. **养鱼**：鱼的装扮、收集、场景和成长。

“养鱼”只在这里作为独立区域出现。它不写入任务完成、不改变提醒、不影响健康结论、不参与项目统计，也不决定记忆是否可信。

## DSH 插件思想如何落到 UI

| Butler 插件 | UI 表现 | 真实数据来源 | 是否允许直接写入 |
|---|---|---|---|
| `fish-expression` | 鱼的状态卡、表情和动作 | `ButlerEvent` | 否 |
| `time-actions` | 任务、计划、提醒、记录的结构化预览 | Room + 规则校验 | 经过确认 |
| `approval` | 确认、拒绝、撤销、权限说明 | 操作历史 | 经过确认 |
| `memory` | 记忆来源、置信度、纠正和召回记录 | 记忆表和来源记录 | 经过用户确认 |
| `proactive` | 今天页建议卡、通知和静默记录 | 候选、证据、预算和安静时段 | 默认不写入 |
| `briefing` | 今日简报、周报和项目解释 | 时间事实和统计 | 否 |
| `fish-game` | 喂养、装扮、收集、成长 | 独立 `fish_game_state` | 只写游戏数据 |

插件的存在不代表天然拥有权限。健康、支付通知、跨应用采集和外部写入仍需单独声明、单独授权和单独验收。

## 统一执行流程

```text
用户输入
  ↓
FishButler 识别意图和边界
  ↓
查询时间事实、项目关系和规则
  ↓
直接回答 / 生成预览 / 请求确认
  ↓
用户确认或拒绝
  ↓
执行可逆动作并写入操作历史
  ↓
发布 ButlerEvent
  ↓
更新时间轴、任务页和鱼的真实状态
```

### 示例：用户说“明天晚上安排两小时复习”

1. 鱼进入“倾听”状态。
2. 解析得到目标、日期、时长和可能的项目。
3. 查询明天空档、现有计划和冲突。
4. 展示计划预览：时间、项目归属、冲突和可替代时段。
5. 用户确认。
6. 写入任务和计划。
7. 鱼进入“完成”状态。
8. 今天页和时间轴刷新，项目统计可回到新记录。

如果解析不完整，鱼应进入“等待确认”，而不是直接创建模糊任务。

## 事件与页面状态的关系

第一阶段可以不新增 Room 表，只建立内存事件总线和状态流：

```text
ButlerEventBus
  ├── UserInput
  ├── InterpretationStarted
  ├── ActionPreviewed
  ├── ConfirmationRequested
  ├── ActionExecuted
  ├── ActionUndone
  ├── ProactiveRunFinished
  └── Error
```

这些事件同时驱动：

- 鱼的状态。
- 输入区的进度。
- 预览底部表单。
- 操作完成反馈。
- 错误和重试入口。
- 今天页的简报刷新。

等事件链稳定后，再接入 Room `v12`、三层记忆、事实键、召回审计、主动预算和安静时段。

## 页面组件需要新增什么

在视觉重构时，优先建立以下共享组件：

1. `ButlerStatusCard`：显示鱼的真实状态和当前说明。
2. `ButlerSuggestionCard`：显示主动候选、证据、价值、风险和静默选项。
3. `ActionPreviewSheet`：展示将要写入的结构化动作。
4. `ApprovalBar`：确认、拒绝、稍后、撤销。
5. `SourceBacklink`：从统计、记忆和建议回到原任务、计划或实际记录。
6. `StateMessage`：统一空、加载、错误、完成和权限不足状态。
7. `FishExpressionSlot`：允许鱼在完整、紧凑和无动画三种模式下展示。

这样可以让项目、周期、期限、复盘、助手和附件页面共享同一套交互语法。

## 视觉层的结合原则

- 鱼是品牌焦点，但不能覆盖主内容。
- 今天页允许使用较大的鱼和状态卡。
- 计划页使用紧凑鱼状态，只在需要协助时出现。
- 复盘页使用小型解释入口，不把鱼做成数据图表本身。
- 等待确认时使用明确的“确认牌”或底部确认条。
- 执行成功时使用短暂庆祝；错误时必须给出原因、影响和重试入口。
- 安静时段不主动播放明显动画，不在没有事件时制造陪伴感。

## 分阶段落地

### 阶段 1：UI 与事件链

不嵌入完整 DSH，不新增 Room 表：

- 将“我的”改为“管家”。
- 新增 FishButler 状态卡。
- 新增 `ButlerEventBus` 和 `ButlerState`。
- 将现有语音解析、预览、确认、执行、撤销接入事件。
- 做一个原创鱼占位表达层。

### 阶段 2：管家能力

- 接入三层记忆。
- 增加来源、事实键、置信度和召回审计。
- 增加主动候选、安静时段、每日预算、冷却和静默收尾。
- 同步 Room 迁移、备份恢复和撤销。

### 阶段 3：养鱼游戏

- 独立游戏状态。
- 喂养、装扮、收集和成长。
- 支持关闭、暂停和重置。
- 不把任务完成绑定为鱼的生存、饥饿或好感条件。

### 阶段 4：兼容层评估

只有在确实需要运行大量 DSH JavaScript 插件，并且已有脚本沙箱、权限隔离和版本管理时，才评估受限 DSH Plugin Adapter。

## 最终组合

```text
时间 Agent
├── 四个用户任务区域：今天 / 计划 / 复盘 / 管家
├── FishButler：输入、记忆、主动、审批、工具和状态
├── 原创大肥鱼：真实状态的可感知表达
├── 养鱼游戏：独立娱乐数据和页面
├── DSH：插件化 Agent 的架构参考
└── Pi Mobile：会话、工具循环、审批和长任务的研究样本
```

用户最终感受到的应该是“时间 Agent 里有一条会工作的鱼”，而不是“时间 Agent 旁边多了一个动画”。

## 视频探索插件：让鱼去外部内容平台活动

新增需求可以作为一个独立的 `video-explore` 插件接入 FishButler。它属于“外部内容探索能力”，不属于任务、习惯或养鱼游戏。

### 与现有 DSH 插件的关系

这部分不是从零设想。已有调研中核对到 `c1overzz/dsh-bili-scroll` 的受限“值班”模式，它已经覆盖了视频平台插件最关键的一部分：

- 定时启动独立 headless 任务。
- 用户配置人设和偏好。
- 每轮只开放少量白名单工具。
- 评论能力默认关闭。
- 专用 profile 和固定工作目录。
- 输出报告和日志，便于审计。

对应证据见 `docs/research/个人管家Agent调研-养鱼DSH与个人Agent方案.md` 的“dsh-bili-scroll 的受限值班模式”一节。

因此，时间 Agent 不应重新发明“视频插件如何被限制”这件事，而应把 DSH 的这套思路映射到本地 `VideoPlatformAdapter`。需要额外补齐的部分是：

| DSH 插件已有参考 | 时间 Agent 需要补齐 |
|---|---|
| 视频平台任务、偏好、白名单、专用 profile | Android 平台授权、WorkManager/前台会话和停止控制 |
| 任务输出、报告和日志 | `VideoShare` 对话消息和来源元数据 |
| 受限工具调用 | 本地强类型 action、预览、确认和撤销 |
| 插件内部状态 | FishButler 状态总线和鱼的真实表达 |

“视频平台连接、自动探索、对话分享、用户授权与可停止控制”中，DSH 插件已经给出了前两项和部分权限模型；对话回流、Android 授权、可撤销写入和明确停止按钮仍然要由时间 Agent 的适配层完成。不能把 DSH 插件的桌面 headless 运行能力直接等同于 Android App 已具备这些能力。

目标体验是：

```text
用户给出兴趣、主题或限制
        ↓
FishButler 选择已授权的视频平台适配器
        ↓
搜索、筛选、查看允许读取的公开信息
        ↓
形成一段自然的分享话题
        ↓
写入主人对话窗口
        ↓
用户像和朋友聊天一样追问、回应或打开原视频
```

### 交互修正：对话优先，不做视频卡片首页

视频卡片不应该成为用户看到的主要交互形态。`dsh-bili-scroll` 已经证明了“插件去平台探索、筛选值得的内容、主动 @ 用户”这条链路是合理的；时间 Agent 要迁移的是它的**内容发现、人格表达和社交交流方式**，而不是把日报搬成一组结构化卡片。citeturn0view0

主人看到的应该是连续聊天，但具体语气、称呼、幽默感、情绪表达和鱼的形象暂不定稿，等待用户提供大肥鱼的人格设定与视觉参考后统一设计。当前只确定消息关系：

```text
外部平台事件
  -> 鱼形成自己的话题和判断
  -> 回到主人私聊
  -> 主人追问
  -> 同一话题继续交流
```

视频链接、标题、平台和来源仍然保留在消息的隐藏元数据或轻量链接预览里，用于追溯和打开原视频，但它们不应该主导对话界面。

### 统一的主人对话

当前 `AssistantConversationPanel` 可以升级为 FishButler 的长期私聊窗口。视频插件产生的不是一个孤立的 `VideoShare` 组件，而是一组连续消息：

```kotlin
data class ButlerConversationTurn(
    val id: String,
    val speaker: Speaker,
    val text: String,
    val createdAt: Long,
    val source: ConversationSource? = null,
    val link: ConversationLink? = null,
    val pendingAction: ButlerAction? = null,
)

data class ConversationLink(
    val platform: String,
    val url: String,
    val title: String? = null,
)
```

鱼可以自然地说：

- “我刚刚看到一个东西，觉得你可能会感兴趣。”
- “这条让我想到你正在做的项目。”
- “我不确定它讲得对不对，我们可以一起看看。”
- “我先不打扰你，等你有空时再继续。”

用户回复后，鱼继续在同一个会话中交流。保存、安排和收藏属于时间 Agent 的本地写入，仍然进入结构化动作预览；评论和发送属于外部社交通道，先检查该平台能力、授权状态和自主规则，未开启时才转为草稿或请求授权。

### 一个共享人格，多个社交通道

用户想迁移的不是“鱼会搜索视频”这一项孤立功能，而是大肥鱼在 B 站、抖音、小黑盒等平台上已经表现出来的**像一个真实的人一样发作品、看内容、参与评论和形成话题**的能力。时间 Agent 应该让这些行为共用一个 FishButler 人格，但每个场景都有独立的身份、权限和可见范围：

| 通道 | 行为 | 默认状态 |
|---|---|---|
| 主人私聊 | 鱼和主人聊天、分享见闻、表达态度、追问和玩耍 | 开启，可设置安静时段 |
| 平台浏览通道 | 按兴趣看公开内容、形成自己的见闻和话题 | 逐平台开启 |
| 平台公开账号 | 发作品、回复评论、参与公开讨论 | 默认关闭，逐平台授权 |

三个通道共享人格风格、兴趣和经过用户确认的长期记忆，但不共享登录态和写权限。主人私聊可以了解鱼在外部平台看到或参与了什么；平台公开账号不能把主人私聊内容、任务、健康、记忆或私人资料带到公开场合。

外部平台的公开发言不能直接等同于主人私聊。按照 `dsh-bili-scroll` 的受限“值班”方式，主人授权的是一个有边界的自主通道，而不是每次替鱼写一句“确认”。鱼可以自己判断是否值得发作品、是否值得回复评论，但只能在主人开启的平台、能力、主题、人设、频率和工具白名单内运行。公开评论默认关闭，主人主动开启后才允许自主回复。主人可以随时暂停、停止或收回平台写权限。公开互动可以设置为：

1. 只生成草稿；
2. 开启受限自主发布，由鱼在规则内自行决定；
3. 对固定主题使用用户预先定义的低风险规则。

评论、发帖、点赞、关注和私信都要记录平台、账号、原文、生成内容、用户授权和最终结果。

### 鱼的社交人格不是模板回复

外部平台账号的目标不是批量发相同文案，而是让鱼在不同场景保持连续、自然、可辨认的表达：

- 看视频时形成“我为什么觉得有趣”的个人感受，而不是只抽取标题。
- 回复评论时先理解上下文，再用鱼自己的语气回应，必要时承认“不确定”。
- 连续讨论时记住当前话题和对方刚刚说过的内容，不把每条评论当成孤立问答。
- 把外部见闻带回主人私聊时，用“我刚才遇到……”的朋友式叙述开场，而不是“发现一条推荐内容”。
- 遇到争议、敏感话题、诱导链接或无法验证的说法时，暂停公开发言并告诉主人原因。

因此，外部平台的作品和评论能力应建模为 `SocialConversationTurn`，视频只是其中一种话题来源；主人私聊中的消息也使用同一套话题和来源链，但显示方式保持自然聊天。

### DSH 能力如何迁移

`dsh-bili-scroll` 负责“去 B 站探索并筛选内容”，`dsh-dafeiyu` 负责“把真实 Agent 状态变成有生命力的表达”。后续时间 Agent 增加的是主人私聊层：

```text
dsh-bili-scroll
  -> 内容发现、筛选、来源
  -> ButlerConversationTurn
  -> FishButler 自然分享
  -> 主人回应
  -> 继续交流或触发受控动作
```

这比“视频卡片 + 操作按钮”更接近用户说的“鱼像朋友一样分享自己觉得有趣的东西”。大肥鱼项目本身也强调它是由真实 DSH session/task/tool 事件驱动的伴侣，而不是独立聊天服务；时间 Agent 可以保留这个原则，把平台浏览、公开交流和主人私聊都接到同一个 FishButler 状态总线上。citeturn0view1

### 首版支持的能力

首版建议采用“API 优先 + 用户可见打开”的组合：

- 搜索公开视频、频道、作者或主题。
- 读取平台允许返回的标题、作者、封面、时长、描述和链接。
- 根据用户明确的兴趣、黑名单、语言和时长偏好筛选内容。
- 生成短摘要、推荐理由和适合继续交流的问题。
- 把内容转成自然语言消息发到 FishButler 对话窗口，链接只作为可选的轻量预览。
- 用户点击后在平台页面或官方播放器中观看。
- 用户明确点选后保存到收件箱、收藏列表或“稍后交流”。

消息只保留必要的来源元数据，用于打开原平台和追溯事实，不把完整视频复制到时间 Agent。标题、作者、平台、链接和摘要依据可以折叠在消息的“来源”入口里；它们服务于信任和打开动作，不主导聊天。摘要只使用平台明确允许读取的描述、公开字幕或用户主动提供的文本。

### 主动探索与外部社交的三种模式

#### 模式一：内容侦察

这是默认模式。鱼定期搜索和筛选内容，但不模拟用户无限滚动，也不在后台持续播放。

用户可以设置：

- 主题和关键词。
- 语言和时长范围。
- 允许的平台。
- 每天最多分享几条。
- 安静时段。
- 不感兴趣的主题和频道。

主动运行结束后，鱼只在对话窗口自然地说少量值得分享的见闻。没有值得分享的内容时保持安静。

#### 模式二：用户发起的陪玩探索

用户在对话中说“陪我找点关于机械键盘的视频”，FishButler 创建一个有时限的探索会话：

- 显示当前平台和搜索主题。
- 显示已找到、已过滤和待分享的数量。
- 用户可以随时停止。
- 鱼把每条内容带回对话，不自动替用户点赞、关注、评论或私信。
- 用户点击视频后，观看行为发生在平台官方页面或播放器内。

这个模式可以让鱼“活跃”，同时保持可见、可控和可回放。

#### 模式三：平台账号自主值班

这是大肥鱼外部账号的迁移重点。主人先为某个平台开启账号和能力，再给出人设、主题、白名单工具、每日预算、冷却时间和安静时段。鱼可以自己判断：

- 是否值得围绕某个主题发布作品。
- 是否值得参与一条评论。
- 是否应该跳过争议、敏感或无法验证的内容。
- 是否把一次外部交流带回主人私聊。

评论能力默认关闭。开启后，鱼可以在规则内自主回复，不需要主人逐条代写；主人可以随时停止任务、暂停平台账号或撤回某项能力。每次发帖和回复都写入平台、账号、上下文、生成内容、授权规则和最终结果，便于回看和撤销后续策略。

### 平台适配器

不要把所有平台写成一个通用的网页点击脚本。每个平台使用单独适配器，并声明能力：

```kotlin
interface VideoPlatformAdapter {
    val id: String
    val capabilities: Set<VideoCapability>

    suspend fun search(request: VideoSearchRequest): List<VideoItem>
    suspend fun details(id: String): VideoItem?
    suspend fun open(item: VideoItem): PlatformOpenResult
}

enum class VideoCapability {
    SEARCH,
    PUBLIC_METADATA,
    AUTHORIZED_LIBRARY,
    OPEN_OFFICIAL_PLAYER,
    SAVE_TO_USER_LIBRARY,
    PUBLIC_CAPTION_ACCESS
}
```

能力必须按平台返回，不能假设每个平台都支持搜索、推荐流、历史、收藏和字幕。

当前可以这样判断：

- YouTube Data API 支持搜索视频、频道和播放列表，也支持部分授权数据；字幕下载要求用户对视频有编辑权限，不能把“任意视频全文总结”作为默认能力。citeturn894218search7turn894218search15turn635219search0
- YouTube 官方政策禁止抓取 YouTube 页面，也禁止通过后台或隐藏播放器播放视频。因此 YouTube 适合做“搜索、自然分享消息和用户可见打开”，不适合做隐藏的无限刷视频服务。citeturn635219search1turn635219search3
- TikTok Display API 主要用于展示已经授权的创作者身份和视频；Research API 面向符合条件的公开内容研究，不能直接假设普通应用可以获得个人推荐流。citeturn894218search0turn894218search3
- 抖音搜索能力当前仍有实验能力和准入限制，不能把文档中的接口直接当成普通开发者可用能力。
- Bilibili 开放平台以开发者认证和授权能力为基础，个人消费侧推荐流、完整历史和任意自动操作需要逐项核实，首版不能承诺。

### 不建议的自动动作

以下动作默认关闭，或必须在用户开启对应的自主通道后运行：

- 无限滚动推荐流。
- 模拟人类连续观看以制造播放量。
- 自动点赞、关注、评论、转发或私信；即使平台允许，也必须由独立能力开关、话题规则、预算、冷却和审计约束。
- 自动下载或重新托管视频和音频。
- 读取未授权的登录数据、私信、收藏和观看历史。
- 使用无障碍服务让鱼在其他 App 中自主规划和执行点击。

Google Play 当前政策明确限制无障碍 API 用于自主发起、规划和执行动作；普通个人管家不能把无障碍服务当成通用视频机器人。citeturn602518search0turn602518search1

### 对话窗口怎么扩展

当前已有 `AssistantConversationPanel`、`AssistantConversation`、结构化 `AssistantReply` 和可确认的 `AssistantPreview`。外部社交能力可以沿用这条链，新增带来源的自然消息和平台事件：

```kotlin
sealed interface ButlerMessage {
    data class Text(val text: String) : ButlerMessage
    data class ActionPreview(val previewId: String, val title: String, val details: String) : ButlerMessage
    data class SocialShare(
        val platform: String,
        val accountId: String?,
        val url: String,
        val text: String,
        val topic: String?,
        val sourceTitle: String?,
    ) : ButlerMessage
    data class SystemState(val state: ButlerState) : ButlerMessage
}
```

`SocialShare` 的 `text` 是鱼真正说给主人听的话，`url`、`sourceTitle` 和 `topic` 只是可选来源。鱼可以围绕视频、作品、评论或平台上的一段讨论进行正常对话：

- “这条为什么有趣？”
- “它和我最近的项目有什么关系？”
- “再找三条更短的。”
- “把第二条放进我的收件箱。”
- “我不喜欢这类内容，以后少推荐。”

其中“解释、比较、继续搜索”属于对话动作；“保存到收件箱”属于时间 Agent 写入动作，仍要经过预览、确认和可撤销历史。

### 后台和 Android 运行方式

视频探索不应默认使用长时间后台播放。Android 前台服务需要显示持续通知，后台启动和设备省电策略也会影响持续运行。citeturn894218search14turn894218search18

建议的运行策略：

1. 默认用 `WorkManager` 做低频内容侦察。
2. 用户主动开始陪玩探索时，使用前台可见会话。
3. 会话有时间上限、分享数量上限和停止按钮。
4. 失败时报告平台、授权、网络或配额原因。
5. 不把内容探索当成提醒可靠性任务。

### 与养鱼游戏的关系

视频探索插件可以让鱼有更多“见闻”和对话素材，但不能把视频观看量转换成鱼的饥饿、健康或任务惩罚。

可以让鱼在对话中说：

- “我找到一条和你正在做的项目有关的视频。”
- “这条比较轻松，适合休息时看。”
- “我不确定这条是否可靠，要不要先打开看看？”

不能让鱼说：

- “你今天没刷视频，所以我生病了。”
- “你不看完这条就不能升级。”
- “我已经替你点赞和关注了。”

视频探索、FishButler 管家状态和养鱼游戏共享角色，但使用三套独立状态：

```text
VideoExploreState  -> 内容探索、来源、授权、分享历史
ButlerState        -> 当前对话、任务、审批、错误
FishGameState      -> 喂养、装扮、收集、成长
```

### 推荐落地顺序

1. 先扩展当前对话窗口，支持连续的 FishButler 自然消息和可选来源链接。
2. 接入一个官方 API 能力明确的平台，先做搜索、详情、打开和“带回主人聊天”。
3. 增加兴趣、黑名单、安静时段和每日分享预算，让鱼形成稳定的见闻习惯。
4. 增加用户发起的陪玩探索前台会话。
5. 增加外部平台账号的作品和评论草稿，验证鱼的社交人格连续性。
6. 最后才开放逐平台的公开发布、评论或其他写操作，并逐项确认授权和平台规则。
