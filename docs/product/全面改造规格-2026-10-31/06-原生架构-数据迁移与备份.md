# 6. 原生架构、数据迁移与备份

> 🏗️ 本章定义原生侧的架构、数据模型迁移、统一执行入口、性能基线与备份 v2。它是第 3–5、7 章的地基，对应第 8 章阶段 1–2。现存代码以基线提交 `660d129` 为准。

## 1. 现状问题（需要解决的根因）

| 问题 | 现状证据 | 影响 |
| --- | --- | --- |
| 导航与状态集中 | `ui/TimeAgentApp.kt` 约 733 行，字符串导航栈＋几十个 `remember` 状态 | 难以保持 Tab 状态、深链、测试 |
| 秒级全局重组 | `TimeViewModel` 每秒更新 `now`，根 UI 订阅 | 耗电、卡顿 |
| 全量快照 | `TimeRepository.observe()` 监听 25 张表，任一变化重建 `LocalSnapshot` | 数据多时卡顿、内存高 |
| 数据库多实例 | `TimeAgentDatabase.open()` 非单例，Activity/Receiver 各自打开 | Room 失效通知不一致、潜在锁冲突 |
| 无 DI | 手动构造依赖 | 测试替身困难 |
| 日程依赖任务 | `ScheduleBlockEntity(taskId: String)` 必填，外键 RESTRICT，且无标题字段 | 无法创建独立日程，导致隐式造任务 |
| 写入路径分散 | UI、鱼工具、接收器各自写库 | 幂等、撤销、版本检查不一致 |

## 2. 目标分层

```
app/
  ui/            Compose 页面与组件（只依赖 ViewModel）
  feature/*/     各功能 ViewModel + UiState（拟建，可逐步迁移）
  domain/        UseCase（纯 Kotlin，可单测），命令/结果模型
  data/          Room DAO、Repository（按需查询）、迁移
  platform/      AlarmManager、通知、前台服务、Glance、CalendarContract、Health Connect
  fish/          鱼的 Android 侧（运行时桥、聊天 UI、悬浮窗）——见第 7 章
core/            纯 Kotlin：时间计算、视口、统计口径、解析（已存在，扩充）
agent-runtime/   保留
```

- **DI**：Hilt。`@Singleton` 提供 `TimeAgentDatabase`、`WorkoutDatabase`、Repository、`CommandExecutor`、`ClockSource`。BroadcastReceiver、Service、Glance 通过 `@AndroidEntryPoint` 或 `EntryPointAccessors` 获取同一实例。
- **导航**：Navigation Compose（类型安全路由），4 个 Tab 各一个嵌套图；深链 `timeagent://today`、`timeagent://item/{type}/{id}`、`timeagent://focus/{id}`、`timeagent://voice`。
- **状态**：每个页面一个 ViewModel，暴露 `StateFlow<UiState>`；UI 用 `collectAsStateWithLifecycle`。
- **时钟**：`ClockSource`（拟建）提供 `minuteTicks: Flow<Instant>`、`secondTicks: Flow<Instant>`（仅在被收集时运行）、`elapsedRealtime()`；测试可注入假时钟。

### 2.1 迁移策略（不可一次性重写）

1. 引入 Hilt 与数据库单例，旧代码通过单例获取数据库（行为不变）。
2. 引入 Navigation Compose 外壳（4 Tab + 语音动作），旧页面作为目的地挂入，先不改内部。
3. 按页面逐个提取 ViewModel、替换全量快照为按需查询。
4. 每一步都可单独发布并通过账本验收。

## 3. 数据模型变更（主库 v12 → v13+）

规则：
- 每次版本 +1 一个迁移，禁止 `fallbackToDestructiveMigration`（现有代码注释已明确此原则）。
- `exportSchema=true` 已开启，迁移 PR 必须提交新的 schema JSON，并用 `MigrationTestHelper` 从 v12 迁移测试（含真实数据样本）。
- 迁移前自动创建本地快照（备份 v2 的“迁移前快照”，见 §6.5），失败时可恢复。

### 3.1 独立日程与幂等表（v13）

`schedule_blocks` 拟建变更：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `taskId` | TEXT **可空** | 旧数据保留。外键保持 RESTRICT（允许 NULL）防止误删；删除任务时由用例询问“同时删除关联日程 / 保留为独立日程（taskId 置空、title 填任务标题）” |
| `title` | TEXT NOT NULL DEFAULT '' | 独立日程标题；关联任务时为空则显示任务标题 |
| `kind` | TEXT NOT NULL DEFAULT 'TIMED' | `TIMED` / `POINT` / `ALL_DAY` |
| `allDayStartDate` / `allDayEndDate` | TEXT? | `ALL_DAY` 用 ISO 日期；`startAt/endAt` 仍填对应时区的 0 点以兼容排序 |
| `timezoneId` | TEXT NOT NULL DEFAULT 设备时区 | 创建时时区 |
| `notes` | TEXT NOT NULL DEFAULT '' | |
| `colorOverride` | TEXT? | |
| `source` | TEXT NOT NULL DEFAULT 'MANUAL' | MANUAL / FISH / VOICE / CALENDAR / TEMPLATE / RECURRING / SAMPLE |
| `sourceRef` | TEXT? | 例如鱼消息 ID、日历事件映射 ID |
| `deletedAt` | INTEGER? | 软删除，支持回收站与撤销 |

SQLite 改可空与外键需重建表：`CREATE TABLE schedule_blocks_new … ; INSERT … SELECT …; DROP; RENAME; 重建索引`，在一个迁移事务内完成。迁移后断言行数一致。同一版本新建 `command_log` 表（见 §4），保证所有新写入路径从第一天起即幂等。

`POINT` 类型：`endAt = startAt`；统计和冲突检测忽略 POINT。

## 4. 统一执行入口（CommandExecutor，拟建）

所有写操作——UI、语音本地指令、鱼的 `time_*` 工具、通知按钮、小组件、日历同步、模板应用——都通过它。

```kotlin
sealed interface Command { val requestId: String; val origin: Origin }
// Origin: UI | VOICE | FISH(sessionId, messageId, toolCallId) | NOTIFICATION | WIDGET | CALENDAR_SYNC | TEMPLATE | SYSTEM

data class CommandResult(
  val requestId: String,
  val status: Status,           // APPLIED | DUPLICATE | CONFLICT | INVALID | NOT_FOUND | FAILED
  val affected: List<EntityRef>,// type, id, newVersion
  val undoToken: String?,       // 对应 OperationEntity 组
  val message: String,          // 给人看的结果
  val conflict: ConflictInfo?   // 期望版本、当前版本、当前值
)
```

规则：
1. **幂等**：`command_log(requestId PRIMARY KEY, commandType, resultJson, createdAt)`。同 requestId 再次提交直接返回首次结果，状态 `DUPLICATE`。保留 30 天后清理。
2. **版本**：修改/删除命令携带 `expectedVersion`；不匹配返回 `CONFLICT`，不写入。
3. **事务**：一个命令（含批量，如模板应用）一个 Room 事务；同时写入现有 `OperationEntity`（before/after 快照）作为撤销单元。
4. **撤销**：`UndoCommand(undoToken)` 也走执行入口；保留现有撤销/重做语义。
5. **事件**：提交成功后发出 `DataChanged(affectedTypes)`，驱动小组件刷新、提醒重排、日历同步防抖任务。
6. **鱼工具**：`FishTimeTools.kt` 的 10 个工具（time_today、time_tasks、time_schedule、time_projects、time_create_task、time_create_plan、time_record、time_complete_task、time_quick_action、time_undo）改为构造 Command 调用执行入口；requestId 由运行时提供的 toolCallId 派生，保证重试不重复写入。
7. **取消**：用户在鱼生成中点“停止”不回滚已 APPLIED 的命令；聊天中工具卡片仍显示并提供撤销。

## 5. 查询与性能

### 5.1 查询改造

- 删除全量 `LocalSnapshot` 依赖（分步：先保留并新增按需 DAO，页面逐个切换，最后删除）。
- 时间轴：`observeBlocks(rangeStart, rangeEnd)`、`observeRecords(rangeStart, rangeEnd)`，范围 = 可见天数 ± 1 天预取；索引 `schedule_blocks(startAt)`、`time_records(startAt)` 已有/补齐，新增 `(deletedAt, startAt)` 复合索引。
- 列表分页：Paging 3 用于历史、记账、实际记录列表。
- 复盘统计：`core` 中纯函数计算，输入为范围内记录；周/月结果缓存于内存，数据变更事件后失效。

### 5.2 性能基线（T1 建立，之后每阶段回归）

| 指标 | 目标 | 测量方式 |
| --- | --- | --- |
| 冷启动到今天页可交互 | ≤ 1.5 s（中端 arm64，1 万实际记录＋2 千日程） | Macrobenchmark `StartupTimingMetric` |
| 时间轴滑动 | P90 帧耗时 ≤ 16ms 的帧占比 ≥ 95% | Macrobenchmark `FrameTimingMetric` |
| 计时运行时 UI 重组 | 仅计时条组件每秒重组 | Compose 重组计数测试 |
| 后台耗电 | 无计时、鱼停止时无唤醒锁、无周期 < 15 分钟任务 | `dumpsys batterystats` |
| 包体 | 不设硬指标；每个版本记录 APK/AAB 大小与各 ABI、rootfs、模型、GIF 占比，变化 > 10% 需说明 | `apkanalyzer` |

生成测试数据的脚本（拟建 `scripts/seed-large-dataset`）用于基准测试，不进入正式包。

## 6. 备份 v2

### 6.1 现状（保留并演进，不删除）

`backup/PersonalBackup.kt`：`BackupEnvelope(format=1, sha256, payload)`，JSON，附件 Base64，`MAX_BYTES = 32MB`；覆盖主库、训练库、附件、部分偏好；跨库失败回滚（rollback 文件）、`PersonalDataGate`、`NonCancellable` 保护。不含 DSH 会话与共同记忆；公共导出排除 Key。

### 6.2 v2 格式

ZIP 归档（流式写入，无总大小上限，仅受存储空间限制）：
```
manifest.json        formatVersion=2, appVersion, createdAt, deviceInfo, parts[ {path, sha256, bytes, schemaVersion} ]
main/                主库一致性快照（VACUUM INTO 生成的 sqlite 文件）
workout/             训练库快照
attachments/         原始文件（不再 Base64）
prefs/               可备份偏好（JSON，排除 Key/凭据）
fish/                DSH 共同记忆与会话导出（见 6.3）
```

### 6.3 一致性快照

- Room 库：在 `PersonalDataGate` 写锁内执行 `VACUUM INTO`（或 `wal_checkpoint(FULL)` 后复制），得到一致文件；不得直接复制活跃中的 db/wal 文件。
- 两个 Room 库各自一致，**不声称跨库原子**；manifest 记录各自快照时间，恢复时作为同一备份点处理。
- DSH 数据：优先调用运行时提供的导出接口（拟建 `fish.export` JSON-RPC 方法，由插件/DSH 侧在其写锁内导出 SQLite 快照）；运行时未运行时，在确认运行时进程已停止后复制其数据目录并校验 `PRAGMA integrity_check`。运行时运行中且导出失败时，备份继续但 manifest 标记 `fish: skipped(reason)` 并提示用户。

### 6.4 恢复

1. 校验 manifest 与每个 part 的 sha256；版本高于当前 App 拒绝恢复并说明。
2. 显示内容摘要（日期、各类记录数、是否含鱼数据），`ConfirmSheet` 说明将覆盖当前数据。
3. 恢复前自动生成当前数据的回滚快照。
4. 停止鱼运行时、取消计时前台服务（保存当前计时）、关闭数据库连接；替换文件；按需执行迁移；重启进程内组件。
5. 任一步失败 → 用回滚快照还原，写恢复日志（`files/restore-log/*.json`）。
6. 恢复后：重排提醒、刷新小组件、日历同步执行全量比对（不盲目把恢复的数据推送到远端，先比对再询问）。
7. 兼容：继续能读取 format=1 的旧备份（使用现有解析代码）。

### 6.5 自动与迁移前快照

- 每次数据库迁移前自动生成本地快照（保留最近 2 份）。
- 可选自动备份：每日/每周到用户选择的目录（SAF 持久授权），保留 N 份。
- 新设备恢复后需重新填写 Key、重新授予权限（文案提示）。

## 7. 可靠性与后台

- 精确提醒：AlarmManager（现有实现）；可延迟工作：WorkManager（同步、导出、报表、清理）。
- 持续计时、专注、训练、鱼运行时：前台服务（类型见第 5 章 N06 与第 7 章）。
- 厂商杀后台无法保证不发生：提供“后台运行诊断”页（电池优化状态、自启动设置引导、最近一次提醒是否准时送达、服务被杀记录），而不是承诺永不中断。
- 进程恢复：计时从数据库恢复；专注按 elapsed 校正；草稿从草稿存储恢复；鱼运行时由用户设置决定是否自动重启。
- 崩溃与诊断：本地崩溃日志；诊断包导出（不含个人内容，可选是否附数据库统计计数），无远程上报。
