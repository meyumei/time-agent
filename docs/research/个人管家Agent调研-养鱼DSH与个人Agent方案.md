# 个人管家 Agent 调研：养鱼就养 DS、DSH 插件机制与时间 Agent 重构方案

- 调研日期：2026-10-28
- 调研对象：DeepSeek Harness（DSH）及“大肥鱼”相关插件、个人 Agent 记忆/主动/权限方案
- 当前产品：时间 Agent `0.11.0 / code17`，Room `v11`
- 本文性质：方案调研与源码审计，不是已经完成的产品实现
- 产品源码状态：本轮未修改

## 1. 结论先行

### 1.1 “养鱼就养 DS”是什么

在本轮可核实材料中，没有找到 DeepSeek 官方把“养鱼就养 DS”注册为产品或项目的证据。它更像社区对 **DeepSeek Harness（DSH）+ 大肥鱼桌宠 + 鱼记忆 + 主动唤醒 + 心情插件** 这一套组合玩法的昵称。

DSH 官方仓库把自己定义为 experimental developer-preview software，并明确写出：

- 未经过安全审计，不能视为安全或生产级软件。
- 会快速迭代，并可能发生破坏兼容性的变更。
- 架构核心是 “Everything is a Plugin”，底层由 Cordis 提供插件组合能力。

因此，对本项目最合理的态度不是移植 DSH，而是借鉴它已经跑通的产品机制。

### 1.2 真正值得迁移的四层能力

1. **持续人格与可见工作状态**：角色不是独立模型，而是真实任务的观察窗口。
2. **会淡忘、但不静默删除、可审计的记忆**：记忆按相关性召回，衰减只降低召回概率。
3. **克制的主动唤醒**：安静时段、每日预算、冷却、去重、静默收尾和“无事不报”。
4. **白名单、可确认、可撤销的执行**：模型输出是受校验的数据，不是任意命令。

“大肥鱼”的主要价值是 **把 Agent 的工作状态变得可感知**，不是提高模型推理能力。它可以启发时间 Agent 的管家形象，但不能直接解决记忆、主动性和执行安全问题。

### 1.3 形象结论

建议制作一个 **原创圆胖鲸鱼/鲸尾管家**。可借用“亲和、圆润、有一点懒散、认真工作时反差明显”的气质，但不要复用现有角色帧、服装、比例、配色组合、动作序列或 DeepSeek 商标。

原因不是审美，而是许可链不一致：

- `PC2005-cloud/dsh-pet` README 明确写角色视觉素材为 `CC BY-NC-SA 4.0`，非商业、署名、相同方式共享，并说明这是社区二创的 DeepSeek“大肥鱼”。
- `QCYTSN/ds-local-pet` 明确写代码 MIT，但角色视觉资产不受 MIT 覆盖。
- `nan89888/dsh-dafeiyu` 当前 `ASSET_LICENSE.md` 声称部分素材来自 `dsh-pet` 且为 MIT，但上游 README 的视觉许可声明与此冲突；旧 BigFish 帧则明确不属 MIT。
- 复用、换色、裁切、重绘得足够接近，都可能仍然涉及原作品权利。

所以“像大肥鱼一样可爱”可以，直接拿“大肥鱼”当角色资产不行。

### 1.4 效果判断

这些项目能证明的是：

- 机制已经写出来并可读。
- 作者为部分版本写了测试、验收和本地基准。
- 部分插件已被个人实际部署使用。

目前没有公开数据能证明：

- 主动建议的长期采纳率。
- 记忆召回的准确率和错误注入率。
- 每日打扰量下降与用户留存提升的关系。
- Android 上的耗电、Doze、HyperOS 后台行为。
- 这套人格/宠物组合能提升幸福感或任务完成率。

因此本文把“代码存在”“测试/构建声明”“个人部署效果”“长期有效性”严格分开。

## 3. DSH 生态的真实边界

### 3.1 架构与许可

`deepseek-ai/deepseek-harness` 当前快照版本为 `0.2.2-alpha.2`，MIT。其核心吸引力是插件化：

- Host、Web、Agent、Session、Tool、UI 都可以通过插件组合。
- 插件可以使用 Cordis 服务发现、生命周期和依赖注入。
- 同一套插件机制可以承载桌宠、主动唤醒、记忆、通知、UI 皮肤等完全不同的能力。

这解释了大肥鱼为什么能“看到工作状态”：它只是订阅 DSH 的 session/task/tool 事件，而不是让另一个模型猜测 DSH 在做什么。

### 3.2 不能直接照搬的原因

- DSH 是开发者预览，不是稳定运行时。
- 插件生态迅速膨胀，不等于单个插件经过安全审计。
- `dshworks/awesome-dsh-plugins` 当前 README 写约 21,928 条条目、12,985 名作者、17 个功能区，这只能说明生态繁荣，不能证明质量、维护性或隐私表现。
- DSH 的 Host 定时器、文件系统、工具沙箱和 Cordis 生命周期不能直接映射到 Android。

时间 Agent 是本地 Android 产品，正确路线是 **重写机制，不搬运宿主**。

## 4. 大肥鱼：真实工作状态可视化

### 4.1 它解决的问题

普通聊天 Agent 在长任务中常常只显示“加载中”，用户不知道它是在：

- 理解请求；
- 调用工具；
- 等待授权；
- 已经完成；
- 失败；
- 还是根本卡住了。

大肥鱼把真实事件映射成动作和文案，使“Agent 在工作”从抽象状态变成可观察反馈。

### 4.2 状态机

`dsh-dafeiyu` 当前源码和 README 使用六类主状态：

- 空闲；
- 思考；
- 工作；
- 等待确认；
- 完成；
- 错误。

多个任务同时运行时，注意力优先级为：

```text
等待确认 > 错误 > 工作 > 思考 > 空闲
```

这比“最后启动的任务永远占屏”更合理，因为用户最需要知道的是“哪里需要我”或“哪里出了问题”。

### 4.3 关键设计

- 状态只来自 DSH 的 session/task/tool 事件。
- 不截图、不读取其他窗口内容。
- 透明置顶窗口只是表现层，不是新的聊天服务或模型。
- 有限动作不会被普通漫游随机打断。
- 多个任务会显示状态列表，而不是假装只有一个任务。
- 可以拖动、点击、展示提示，但这些交互不改变任务事实。

### 4.4 作者记录的运行效果

`dsh-dafeiyu/docs/ACCEPTANCE.md` 记录了单机 Windows alpha 基线：

- 热启动 Helper：约 `1.195 s`。
- 父子进程工作集合计：约 `74.2 MB`。
- 私有内存合计：约 `32.1 MB`。
- 5 秒空闲 CPU 归一化：约 `0.14%`。
- npm 压缩包：约 `54.2 MB`。

这些数字只能作为“这套桌宠在该作者设备上可以运行”的证据，不是 Android 或跨设备保证。桌面版体积、Python/Qt/Electron 依赖也不适合直接搬到手机。

### 4.5 对时间 Agent 的启示

时间 Agent 应做一个轻量的 **应用内管家状态总线**：

```text
Idle
Listening
Thinking
Working
WaitingConfirmation
Done
Error
Resting
```

状态必须来自真实流程：

- 录音中 -> Listening
- 本地解析/云端请求 -> Thinking
- 查询、写入、重算建议 -> Working
- 需要用户确认 -> WaitingConfirmation
- 操作完成 -> Done，短时间后回 Idle
- 失败 -> Error，可重试
- 安静时段或无任务 -> Resting

不能因为“动画需要”伪造工作状态，否则用户会失去对它的信任。

## 5. 鱼记忆：可解释的淡忘，而不是删除

### 5.1 默认参数

`Yuuyuko-uu/dsh-fish-memory` 当前快照为 `1.3.8`，MIT。源码默认值包括：

- 普通事件半衰期：30 天。
- 情绪半衰期：7 天。
- 基础权重：`0.55`。
- 鲜活度权重：`0.25`。
- 重要度权重：`0.15`。
- 情绪权重：`0.05`。
- 证据门槛：`0.35`。
- 单次最多注入 6 条，合计不超过 800 字。
- 每天最多自动记录 8 条。
- 长期事实每轮固定带 2 条。
- 召回审计最多保留最近 100 次。

### 5.2 设计亮点

#### 淡忘不是删除

记忆越久，召回概率越低，但记录仍在。用户可以查看、修正、恢复。

#### 事实键

同一类事实使用稳定键，例如“睡觉时间”，值不进入键。新值可把旧值标为“已被取代”，而不是静默覆盖。

#### 召回审计

每次召回能解释：

- 命中了什么线索；
- 分数是多少；
- 是否超过门槛；
- 是否因条数、字数、重复或长期事实名额被挤出；
- 最终注入了哪些记忆。

#### 自动写入有配额

每天最多自动记录固定数量，防止模型把每句话都变成永久记忆。

### 5.3 借鉴时不能照抄的部分

- `0.55/0.25/0.15/0.05` 是该项目在中文对话场景下的经验值，不是通用最优解。
- 词频、词典和字符串相似度适合桌面文本，但 Android 上要考虑包体、中文分词、内存和耗电。
- “记忆注入 800 字”不能直接套给时间 Agent，因为任务上下文、健康摘要和用户约束更结构化。
- 召回的“分数高”不等于事实正确；仍需要来源、证据和用户确认。

### 5.4 时间 Agent 应采用的三层记忆

| 层 | 内容 | 是否衰减 | 写入方式 |
|---|---|---|---|
| 稳定画像与约定 | 称呼、偏好、禁忌、长期作息约定 | 不按时间衰减，可失效/撤回 | 显式确认优先 |
| 经历与事项 | 做过什么、何时发生、结果、经验 | 按半衰期降低召回权重 | 事实候选/确认 |
| 当前工作状态 | 当前项目、任务、计划、最近操作 | 随任务状态过期 | 事务事实，不由模型猜 |

稳定画像不能自动从旧任务推断项目归属；每个统计必须回到原任务、计划或实际记录。

## 6. 主动唤醒：不打扰也是完成

### 6.1 机制

`john-walks-slow/dsh-proactive` 当前快照为 `0.3.2`，包内声明 MIT。仓库根目录没有 LICENSE，但包目录有 LICENSE，分发时应以实际包内容为准并保留说明。

主要能力：

- 单次、周期、cron、文件时间表。
- 随机抖动，避免所有任务同一秒醒来。
- 安静时段。
- 每日可见消息预算。
- 每小时唤醒上限。
- 最近活动时间门限。
- 用户委托提醒与模型自主跟进分开。
- `proactive_reclaim` 静默收尾。

### 6.2 最值得学的两个决定

#### “无事可报”是合法结果

到点不等于必须说话。没有新信息、没有价值、风险太高或用户在忙时，可以静默结束。

#### 静默唤醒也要审计

静默收尾在模型可见上下文中折叠成墓碑：默认模式保留简短原因，约 200–400 字节；极简模式只留 ID 和时间，约 70 字节。人工日志仍保留完整执行轨迹，因此既控制上下文，也不会丢失可追责性。

### 6.3 Android 映射

| DSH 机制 | Android 对应 |
|---|---|
| Host 定时器 | `AlarmManager` / `WorkManager` |
| 用户明确委托的准点提醒 | `AlarmManager` 精确/非精确降级 |
| 可延迟整理、摘要、反思 | `WorkManager`，不保证准点 |
| 安静时段 | 本地配置 + 通知渠道策略 |
| 每日预算 | 本地计数 + 跨重启持久化 |
| 静默收尾 | 只写审计，不产生通知 |

`SuggestionCoordinator` 目前每 60 秒在 UI scope 刷新，只能算前台刷新，不是系统级主动唤醒。不能把它当后台定时器使用。

### 6.4 主动管家的判断链

```text
候选生成
  -> 证据与置信度
  -> 价值和风险
  -> 时效与去重
  -> 安静时段与预算
  -> deliver / defer / ask / silent
  -> 写审计
```

每次主动行为都应有：

- 来源实体；
- 生成原因；
- 证据；
- 有效期；
- 去重键；
- 打扰等级；
- 用户动作：采纳、忽略、延后、撤销；
- 最终决策和结果。

## 7. 鱼的心情：只做表达，不做事实

`Yuuyuko-uu/dsh-feiyu-mood` 当前快照为 `0.7.6`，MIT。

每轮通过短模型调用输出：

- `moodDelta`；
- 七类情绪变化；
- 一句理由；
- `confidence`。

源码默认总心情半衰期为 12 小时，单类情绪半衰期约 90 分钟。README 中残留的 3 小时描述与最新代码不一致，应以源码为准。

值得借鉴：

- 低置信度只写后台，不进入角色口吻。
- 不允许因为“用户惹它生气”而真实降低服务质量。
- 情绪可以影响语气和动作，但不能覆盖任务事实、截止时间、健康结论。

对时间 Agent 的建议：

- 第一阶段不做每日情绪模型。
- 若以后要做，只作为 `ExpressionState`，与任务/记忆数据库分离。
- 情绪不得触发删除、改期、记账、打卡等写操作。

## 8. 其他个人 Agent 方案

### 8.1 AutoPersona

当前提交为 `e6f837623dfa4f59635c0532730f78e92122169c`。README 描述三层记忆：

- Trajectory Memory：历史请求、动作、结果、可复用经验。
- Workspace Memory：任务状态、环境状态、当前上下文。
- Persona Memory：偏好、约束、适用主题和帮助策略。

其关键决策是 `clarify`：证据不足时停下来问具体问题，而不是用最可能的偏好猜。

可借鉴：

- 证据检索；
- 澄清优先于猜测；

- README 明确当前发布没有开源许可证，版权与复用权限保留。
- README 声称 46 项确定性测试，但本轮未重跑。

## 9. dsh-bili-scroll 的受限“值班”模式

`c1overzz/dsh-bili-scroll` 当前 HEAD 为 `2170499bb1aedf222874dbf2b6dadb65036681fa`，MIT。

它最有价值的地方不是“刷 B 站”，而是把自主任务关进很小的权限盒：

- 到点启动独立 headless 任务。
- 用户可配置人设和偏好。
- 每轮只开放少量白名单工具。
- 评论能力默认关闭，由用户主动开启。
- 专用 profile 的工作目录被限定在插件家目录。
- 2026-10-24 起，那一轮没有文件系统、命令和联网。
- 路径由插件写死，不接受模型传路径。
- 隐私红线写死在提示词，不靠模型自觉。
- 输出报告和日志，便于审计。

对管家 Agent 的启示：

```text
不是给模型“整台手机”
而是给当前任务最小的一组强类型动作
```

时间 Agent 已有 `DeepSeekProtocol.kt` 的扁平、白名单、强类型 JSON action，这是非常正确的方向。后续应保留并强化，而不是为了“更自由”引入通用 shell、文件系统或任意 URL 工具。

## 10. “效果”如何理解

### 10.1 可核对的效果

| 能力 | 可核对结果 | 证据边界 |
|---|---|---|
| DSH 插件化 | 源码、Cordis 架构、插件生态 | 仍是 developer preview |
| 大肥鱼状态 | 六态、事件驱动、优先级、单机基准 | 无长期多设备数据 |
| 鱼记忆 | 衰减、事实键、召回审计、配额 | 未证明跨场景准确率 |
| 主动唤醒 | 安静时段、预算、静默收尾 | 未证明降低打扰或提高完成率 |
| 心情 | 独立表达层、置信度门槛 | 不适合事实判断 |
| 受限值班 | 工具白名单、工作目录、隐私红线 | 未证明所有平台均等效 |

### 10.2 不能宣称的效果

- 不能写“完整测试通过”，除非本轮重新执行并保留日志。
- 不能写“长期有效”，除非有跨用户、跨设备、足够时长的数据。
- 不能把 registry 收录数当安全性、维护性或用户满意度。
- 不能把桌宠好看等同于 Agent 更聪明。
- 不能把 managed benchmark 当本地自托管效果。

### 10.3 建议建立的产品指标

- 建议展示数、采纳率、忽略率、延后率、撤销率。
- 记忆召回准确率、错误注入率、事实取代错误率。
- 每日主动消息数、安静时段违规数、预算超限次数。
- 唤醒次数、耗电、状态延迟、动画掉帧。
- 建议后任务完成率、回滚失败率。
- 用户打开简报后的下一步操作率。

## 11. 时间 Agent 当前实现审计

### 11.1 已有优势

当前版本 `0.11.0 / code17`，主数据库 Room `v11`。

现有基础不差：

- 本地优先，云模型只处理语言理解。
- `AssistantConversation.kt` 界面保留最近 20 轮，云端只接收最近 8 轮。
- `DeepSeekProtocol.kt` 是扁平白名单 action，模型返回数据而不是可执行命令。
- `SuggestionEngine.kt` 已有逾期任务、今日空档、短睡眠三类建议。
- 建议卡已有 `type/title/detail/dedupKey/taskId/taskVersion/proposedStartAt/proposedEndAt/forDate/expiresAt`。
- `SuggestionCoordinator.kt` 能每 60 秒及仓库变化刷新。
- `DailyBriefing.kt` 已有下一项、截止任务、空闲、睡眠、训练、健康来源状态。
- `PersonalMemoryEntity.kt` 已有类型、来源、确认、有效期、星期和时间窗规则。
- `ReminderAlarms.kt` 已有精确闹钟与 `setAndAllowWhileIdle` 降级。
- `ReminderReceivers.kt` 已处理开机、包更新、时间/时区变化和精确闹钟权限变化。
- `TimeAgentDatabase.kt` 要求显式迁移，源码明确禁止破坏性迁移。
- `BackupSql.kt` 使用显式 `BackupTables.main` 表列表。

### 11.2 主要缺口

| 缺口 | 当前状态 | 影响 |
|---|---|---|
| 人格配置 | 主要是系统提示词和少量界面文案 | 语气、边界、主动性不可独立调 |
| 工作状态总线 | 无统一状态模型 | 管家形象只能猜测或做假动画 |
| 长期记忆检索 | 只有显式规则、星期避让和时间窗 | 不会按当前话题召回经历 |
| 记忆可信度 | 无证据、置信度、重要度、事实键 | 难以处理冲突和错误记忆 |
| 记忆审计 | 无召回与未召回原因 | 出错后无法解释 |
| 主动引擎 | 三类规则 + 前台 60 秒刷新 | 不能后台克制地持续工作 |
| 主动预算 | 无每日/每小时/冷却统一控制 | 容易重复打扰 |
| 静默收尾 | 无显式机制 | “无建议”与“失败”混在一起 |
| 建议价值判断 | 规则存在但无统一评分 | 难比较不同类型候选 |
| 工具权限分层 | 已有白名单，但无按场景最小权限 | 每次请求能力仍偏宽 |
| 形象层 | 无原创管家资产 | 无法形成稳定角色识别 |
| 效果看板 | 无采纳/忽略/撤销等指标 | 无法证明迭代是否有效 |

## 12. 推荐目标架构

```text
用户语音/文字
    |
    v
人格与边界层
  - 称呼、语气、主动性
  - 确认阈值、敏感主题
    |
    v
管家事件总线
  - 状态事件
  - 任务/计划/记录变化
  - 记忆写入/召回
    |
    +--> 三层记忆
    |      1. 稳定画像与约定
    |      2. 带时间的经历和事项
    |      3. 当前项目、任务和环境状态
    |
    +--> 主动管家控制器
    |      候选 -> 证据 -> 价值/风险 -> 安静/预算 -> 决策
    |
    +--> 白名单 Agent 执行层
           强类型 action + 预览 + 确认 + 撤销
    |
    v
简报 / 建议 / 管家状态 / 可选情绪表达
```

### 12.1 关键原则

1. **事实本地、表达可云**：云端可以理解语言，不保存完整人生账本。
2. **状态只由真实事件产生**：形象不能自行进入“工作中”。
3. **记忆只降低召回，不静默删除**。
4. **主动的默认答案可以是不说话**。
5. **模型只能选白名单动作，不能自由执行系统能力**。
6. **建议必须有来源、原因、有效期和退出路径**。
7. **新表必须同时处理 Room 迁移、备份恢复和撤销**。
8. **桌面小组件、AppWidget、Glance 不在本轮范围**。

## 13. 数据模型与迁移建议

### 13.1 人格配置

不建议把完整人格只存成一大段 prompt。建议独立配置：

- 管家名称；
- 称呼用户方式；
- 语气强度；
- 主动性等级；
- 默认安静时段；
- 每日主动上限；
- 需要确认的动作类型；
- 禁用话题/敏感等级；
- 是否启用心情表达。

可先使用 DataStore/本地配置；若需要多套人格、历史和备份，再进入 Room。

### 13.2 扩展现有记忆

优先考虑在 `PersonalMemoryEntity` 上增加：

- `factKey`：同一事实的稳定键；
- `confidence`：证据置信度；
- `importance`：重要度；
- `sensitivity`：敏感等级；
- `evidenceJson`：来源和证据摘要；
- `halfLifeDays`：衰减速度；
- `supersededBy`：被哪条替代；
- `lastRecalledAt`；
- `recallCount`；
- `status`：active/superseded/rejected/archived。

新增 `memory_recall_audits`：

- 查询摘要；
- 时间；
- 候选数量；
- 入选/未入选 ID；
- 排序分数；
- 未入选原因；
- 注入字数和条数；
- 模型版本/本地规则版本。

这会把“记忆错了”从不可解释变成可定位。

### 13.3 建议与主动决策

现有 `AgentSuggestionEntity` 可以复用，不必再复制一套建议实体。建议补充：

- `sourceKind/sourceId`；
- `reasonCode`；
- `evidenceJson`；
- `confidence`；
- `riskLevel`；
- `priorityScore`；
- `quietPolicy`；
- `requiresConfirmation`；
- `state`：candidate/delivered/deferred/dismissed/accepted/expired/silent。

另建 `proactive_runs` 记录每次唤醒：

- 触发来源；
- 候选数量；
- 最终决策；
- 是否静默；
- 预算扣减；
- 错误原因；
- 开始/结束时间；
- 用户是否撤销。

### 13.4 迁移与备份硬约束

- Room `v11 -> v12` 必须写显式 migration。
- 禁止 `fallbackToDestructiveMigration`。
- 新表必须加入 `BackupTables.main`。
- 新字段必须验证旧 JSON 备份的缺省值兼容。
- 必须有“创建数据 -> 备份 -> 清空 -> 恢复 -> 对比”的回归测试。
- 删除/取代记忆要有撤销路径，不能只做物理删除。

## 14. Android 运行约束

### 14.1 调度

- 用户明确承诺的准点提醒：`AlarmManager`。
- 精确闹钟无权限时：保留现有非精确降级，并明确告知用户。
- 可延迟的整理、摘要、反思：`WorkManager`，最短约 15 分钟且不保证准点。
- 前台 UI 的 60 秒刷新不能作为后台能力。
- 必须实测 Doze、省电模式、HyperOS 自启动/后台限制。

### 14.2 通知

- 主动建议与用户委托提醒使用不同通知类别。
- 同一候选只能存在一个活动通知。
- 忽略/延后/完成后要撤销对应通知。
- 安静时段违规要有本地审计，不只在 UI 隐藏。
- 每日预算跨进程、跨重启持久化。

### 14.3 形象与性能

- 只做应用内角色，不做桌面小组件。
- 优先矢量/低帧率序列/局部动画，避免高内存视频解码。
- 支持减少动效。
- 动画状态由 Flow 驱动，不直接读数据库。
- 动画卡顿和耗电纳入验收，不以“看起来流畅”代替测量。

## 15. 分阶段路线图

### 阶段 0：冻结机制设计

产出：

- 人格配置字段；
- 状态枚举；
- 记忆字段和迁移草案；
- 主动决策状态机；
- 隐私与视觉资产清单。

完成条件：

- 不写产品代码也能评审；
- 所有新增字段有来源、默认值、备份和回滚说明；
- 明确哪些能力不做。

### 阶段 1：管家内核与状态总线

产出：

- `ButlerState` 事件模型；
- 人格配置；
- 真实流程状态映射；
- 应用内管家占位形象；
- 无主动打扰。

完成条件：

- 录音、解析、执行、确认、完成、失败都能驱动状态；
- 页面重启不会伪造“工作中”；
- 状态切换延迟和动画成本可测。

### 阶段 2：三层记忆

产出：

- 现有 `PersonalMemoryEntity` 扩展；
- 事实键；
- 证据和置信度；
- 召回排序；
- `memory_recall_audits`；
- Room `v12` migration；
- 备份/恢复回归。

完成条件：

- 新旧数据迁移无损；
- 相同事实键可标记取代而非静默删除；
- 能解释某条记忆为何入选/未入选；
- 用户可以纠正、停用、恢复。

### 阶段 3：主动管家控制器

产出：

- 统一候选；
- 价值/风险/时效评分；
- 安静时段、每日预算、每小时上限、冷却；
- deliver/defer/ask/silent；
- `proactive_runs` 审计；
- 复用现有提醒和通知。

完成条件：

- “无事可报”不会产生空通知；
- 用户委托提醒与自主跟进分离；
- 建议可忽略、延后、撤销；
- HyperOS 真机后台测试完成。

### 阶段 4：原创胖鲸鱼管家形象

产出：

- 角色设定；
- 原创比例、配色、服装、动作；
- 6-8 个真实状态动画；
- 无障碍和低功耗方案；
- 素材来源与许可台账。

完成条件：

- 不复用现有大肥鱼帧和 DeepSeek 商标；
- 视觉与状态机一一对应；
- 低端机无明显掉帧；
- 用户可关闭动画。

### 阶段 5：可选表达增强

产出：

- 低置信度心情/语气；
- 离线反思；
- 云端意图评估；
- 周报式记忆整理。

完成条件：

- 不参与事实判断；
- 不覆盖任务/健康数据；
- 不因情绪改变提醒可靠性；
- 云端只拿最小化、脱敏、用户允许的内容。

## 16. 安全、隐私与视觉许可

### 16.1 数据

- 不索取 API key、密码、支付凭据。
- 健康原始数据默认本地。
- 私人聊天、通讯录、截图不进入长期记忆。
- 云端请求只发送当前任务所需的最小摘要。
- 记忆写入前进行敏感等级分类。
- 敏感记忆必须显式确认，且支持彻底删除。

### 16.2 Prompt Injection

- 外部网页、通知、聊天内容一律视为不可信数据。
- 模型输出必须经过 action schema 校验。
- 工具描述不能由外部数据动态扩展。
- 高风险动作：先预览、再确认、保留撤销。
- 不允许模型自行改权限、开无障碍、安装应用或读取任意文件。

### 16.3 视觉资产

建议资产策略：

- 自建原创角色设定和关键姿态。
- 保存提示词、参考图授权、生成日期、人工修改记录。
- 不将 `dsh-pet`、`ds-local-pet`、`dsh-dafeiyu` 的角色帧打进 release。
- 不使用 DeepSeek logo、名称暗示官方背书。
- 若未来商业化，所有素材必须有可用于商业分发的明确许可。

## 17. 最终建议

### 推荐采用

1. 大肥鱼式“真实工作状态可视化”。
2. 鱼记忆式“淡忘、事实键、召回审计”。
3. 主动唤醒式“安静时段、预算、静默收尾”。
4. bili-scroll 式“最小工具白名单、路径写死、日志可审计”。
5. AutoPersona 式“三层记忆 + 证据不足先澄清”。
6. Mem0/Generative Agents 的“多信号召回 + 轻量反思”，但缩小到时间管理场景。

### 暂不采用

- 直接移植 DSH 或 Cordis。
- 通用文件系统、shell、任意网络工具。
- 复杂社会模拟。
- 每日自动心情模型作为第一阶段核心。
- 复用现有大肥鱼角色资产。
- 桌面小组件/AppWidget/Glance。

### 最合理的首个开发切片

先做“管家内核 + 状态总线 + 原创占位形象”，不改数据库。第二阶段再做记忆 `v12`。这样可以先验证：

- 真实状态是否能稳定驱动形象；
- 用户是否愿意看这个角色；
- 状态切换是否影响主流程性能；
- 后续记忆和主动能力是否有清晰接入点。
