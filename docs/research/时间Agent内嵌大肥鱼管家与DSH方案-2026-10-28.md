# 时间 Agent 内嵌大肥鱼管家与 DSH 方案

> 本文保留早期内嵌架构讨论。当前起步路线更新为复用 SurfCore 电脑宿主与 QQ 私聊，时间 Agent 先整理功能和页面。具体取舍见[统一启动方案](时间Agent与大肥鱼-统一启动方案-2026-10-28.md)。

- 日期：2026-10-28
- 当前时间 Agent：`0.11.0 / code17`，Room `v11`
- 设计目标：在时间 Agent 内部养一条原创大肥鱼，并让这条鱼成为真正的管家 Agent
- Pi Mobile 的用途：研究成熟 Agent 的运行方式、状态、工具、会话和审批设计
- 本文性质：纠正后的目标架构与实施建议，本轮未修改产品源码

## 1. 目标重新定义

目标不是让时间 Agent 和 Pi 各自拥有一个 Agent，再通过外部交接协作。

目标是：

```text
时间 Agent
  └── 大肥鱼管家 Agent
        ├── 持续人格
        ├── 时间任务理解
        ├── 记忆
        ├── 主动跟进
        ├── 工具审批
        ├── 管家状态
        ├── 胖鱼工作状态表达
        └── 独立养鱼游戏
```

这条鱼既是：

- 时间 Agent 的界面角色；
- 用户可以长期相处的管家人格；
- 任务、提醒、计划和复盘的统一入口；
- 主动跟进和记忆的承载者；
- 真实工作状态的可视化对象。

“养鱼”是产品交互和人格表达；“管家”是实际功能；两者必须由同一个 Agent 状态和同一套事实驱动。

## 2. Pi Mobile 应该怎么利用

手机 Pi Agent 不作为时间 Agent 的外置管家，而作为研究样本和工程参考。

重点研究 Pi 的这些机制：

- Agent 如何维持会话和工作状态；
- 工具调用如何流式展示；
- 工具执行前如何审批；
- 扩展 UI 如何向用户请求确认；
- 多轮任务如何暂停、恢复和继续；
- 工作区、会话、模型配置如何隔离；
- 长任务如何通过前台服务保持运行；
- Agent 出错后如何报告和恢复；
- 复杂任务如何通过工具循环完成。

应该学习的是内部机制和边界，不是把 Pi Mobile 的完整 Node/Pi 运行时复制进时间 Agent。

当前 Pi Mobile 已经是一个相对完整的独立 Agent 工作台。它的 APK、内嵌 Node、Pi CLI、会话目录、模型认证、前台服务和工具审批都属于另一套运行时。把它整体嵌入时间 Agent，会让时间 Agent 变成“时间数据库 + 第二套 Node Agent 系统”，复杂度和风险都会显著增加。

## 3. DSH 是否应该嵌入

结论分三层：

| 方案 | 判断 | 建议 |
|---|---|---|
| 完整嵌入 DSH Host、Cordis 和全部插件 | 暂不采用 | 不适合第一版 Android 时间 Agent |
| 直接复制大肥鱼或 DSH 宠物素材 | 不采用 | 视觉资产许可和原创性不清晰 |
| 借鉴 DSH 的插件模型，在时间 Agent 内实现轻量 Butler Kernel | 采用 | 这是最适合当前项目的路线 |

### 3.1 为什么不直接嵌入完整 DSH

完整 DSH 主要解决的是通用 Agent 宿主和插件编排问题，而时间 Agent 还必须处理 Android 特有约束：

- Room 数据库和显式迁移；
- AlarmManager、WorkManager 和系统广播；
- Android 生命周期、Doze 和厂商后台限制；
- 通知权限和精确闹钟权限；
- 健康数据和敏感内容边界；
- 本地密钥与备份排除；
- 任务、计划、实际记录和撤销的一致性；
- 应用包体和耗电；
- 模型请求失败时的本地降级。

如果把 DSH Host 直接搬进来，至少要同时维护：

```text
Android App
  + Room / Compose / AlarmManager
  + DSH Host
  + Cordis 插件生命周期
  + Node 或其他脚本运行时
  + Agent 会话
  + 工具权限
  + 模型认证
```

这会把“学习 DSH 的 Agent 方法”变成“维护一套新的 Agent 操作系统”。

### 3.2 为什么要借鉴 DSH 的插件模型

DSH 最值得借鉴的不是桌宠本身，而是：

- 能力按插件拆分；
- 插件有生命周期；
- 插件通过事件和服务通信；
- 宿主统一管理状态；
- 工具和 UI 请求可以被拦截；
- 宠物、记忆、主动唤醒、心情可以组合；
- 不同能力不必全部塞进一个巨大 Prompt。

时间 Agent 可以实现一个更小、更适合 Android 的版本：

```text
ButlerKernel
  ├── ButlerEventBus
  ├── ButlerStateStore
  ├── ButlerPluginRegistry
  ├── ButlerToolRouter
  ├── ButlerMemoryService
  ├── ButlerProactiveService
  └── ButlerExpressionService
```

这不是移植 DSH，而是把 DSH 的架构思想变成 Kotlin/Android 原生实现。

## 4. 大肥鱼应该是什么

大肥鱼不能只是一个漂浮在页面上的动画，也不能只是一个聊天头像。

它应该是一个有以下结构的管家 Agent：

```text
FishButler
  ├── Persona：怎么说话、怎么称呼用户、哪些事情必须确认
  ├── State：空闲、思考、工作、等待确认、完成、错误、休息
  ├── Memory：用户明确约定、经历、当前时间状态
  ├── Planner：把自然语言变成时间动作或待确认方案
  ├── Proactive：判断何时跟进、何时安静
  ├── Tools：查询、创建、修改、提醒、复盘
  ├── Guard：权限、敏感数据、冲突和撤销
  ├── Expression：鱼的真实工作状态动作与表情
  └── FishGame：独立的养鱼互动、装扮和成长
```

模型只是其中的语言理解和方案生成部分。模型不能直接成为事实源，也不能直接写数据库。

### 4.1 从“大肥鱼账号”迁移什么能力

用户希望迁移的不是一个视频推荐入口，而是大肥鱼在 B 站、抖音、小黑盒等平台上已经形成的社交人格：

- 它可以发布自己的作品，而不是只转发链接；
- 它可以读懂评论上下文，用正常语气回复；
- 它可以围绕一个话题连续交流，表现出稳定的兴趣和态度；
- 它可以把外部平台遇到的见闻带回时间 Agent，像朋友一样和主人聊天；
- 它可以在主人追问时继续解释、玩笑、比较或承认自己不确定。

因此，FishButler 的 `Persona` 不能只保存称呼和语气，还要包含“主人私聊”和“外部平台账号”两类社交身份。它们共享人格风格和经过确认的长期记忆，但分别拥有：

```text
FishButler Persona
  ├── OwnerChatIdentity
  │     └── 与主人私聊、分享见闻、继续玩耍
  └── PlatformIdentity[platform, account]
        └── 发作品、回复评论、参与公开讨论
```

外部身份默认没有写权限。主人开启后，可以选择只生成草稿、逐条确认，或启用明确的低风险自主规则。鱼也可以在主人私聊中分享“我想回复这条评论”的想法，但这不是每次公开互动都必须经过的人工审批步骤。主人私聊的任务、健康、记忆和私密内容不能自动流向公开账号。

视频探索只是外部社交能力的一种来源。更通用的事件应命名为 `SocialConversationTurn`，至少记录平台、账号、话题、上下文、鱼的表达、授权状态和最终结果；`VideoShare` 只作为其中一种可选来源，而不是主要界面形态。

这里要参考 DSH 插件的关键区别：主人授权的是“鱼可以在边界内自主运行”，不是“每个动作都由主人逐条代写或确认”。平台账号开启后，鱼可以自己决定是否值得发作品、是否值得回复评论；宿主只提供限定平台、限定能力、限定主题、限定工具、预算、冷却、安静时段和停止按钮。评论能力默认关闭，公开互动必须有独立开关和完整日志。遇到敏感话题、无法验证的内容、风控或规则不匹配时，鱼应跳过并保持安静。

## 5. “养鱼”功能和管家状态分层

这里要严格分成两层：

1. **管家状态表达层**：鱼根据时间 Agent 的真实事件表现正在倾听、思考、工作、等待确认、完成或出错。
2. **养鱼游戏层**：用户和鱼之间的喂养、装扮、收集、互动和成长，是独立的娱乐内容。

养鱼游戏不参与任务写入、提醒可靠性、项目统计、记忆判断或权限决策。真实时间事件也不强行转换成喂鱼任务。两层可以共享同一个角色和页面，但数据、规则和验收分别处理。

### 5.1 鱼的状态来自真实事件

| 真实事件 | 鱼的表达 |
|---|---|
| 用户打开时间 Agent | 鱼醒来或探头 |
| 正在解析语音 | 鱼侧耳倾听 |
| 正在生成计划 | 鱼翻计划本 |
| 正在执行本地写入 | 鱼认真工作 |
| 等待用户确认 | 鱼举起确认牌 |
| 提醒即将到点 | 鱼查看时钟 |
| 任务完成 | 鱼短暂庆祝 |
| 执行失败 | 鱼说明原因并提供重试 |
| 安静时段 | 鱼休息 |
| 没有新信息 | 鱼保持安静 |

状态必须由事件驱动，不能为了动画随机伪造“思考中”。

大肥鱼的具体外观、比例、服装、动作风格和素材来源暂不预设，等待用户后续提供形象参考后再建立视觉规范。

### 5.2 鱼的心情只影响表达

可以有心情，但心情必须是表达层：

- 任务积压时表现为有点担心；
- 用户连续完成任务时表现为开心；
- 长时间没有互动时表现为安静；
- 连续失败时表现为需要协助。

心情不能改变：

- 提醒是否发送；
- 任务是否完成；
- 健康结论；
- 数据是否写入；
- 冲突检查；
- 用户撤销权。

### 5.3 养鱼游戏独立设计

养鱼互动可以作为单独的娱乐系统设计，例如：

- 喂食、清洁、装扮、收集和场景布置；
- 鱼的动画、状态变化和轻量成长；
- 与真实时间管理无关的小游戏和奖励；
- 离线可玩的本地内容；
- 用户可以关闭、暂停或重置游戏进度。

第一版不要求这些互动对应真实任务，也不把“今天有没有完成任务”作为鱼是否饥饿、是否生病或是否掉好感的依据。这样可以避免把时间管理变成带压力的游戏惩罚。

养鱼游戏数据建议单独放在 `fish_game_state` 或独立的本地存储中，不写入任务、计划、记录和个人记忆表。

### 5.4 鱼的成长不能诱导用户

成长只属于养鱼游戏，不改变管家能力和时间数据。可以设计等级、装扮、场景和收集内容，但不能通过连续签到、焦虑惩罚、强制喂养或虚假损失诱导用户频繁打开应用。

## 6. 管家内核的推荐接口

不需要一开始实现通用 DSH 插件系统。先定义时间 Agent 自己能控制的最小接口。

### 6.1 事件

```kotlin
sealed interface ButlerEvent {
    data class UserInput(val text: String) : ButlerEvent
    data class SpeechStarted(val requestId: String) : ButlerEvent
    data class InterpretationStarted(val requestId: String) : ButlerEvent
    data class ActionPreviewed(val actionId: String) : ButlerEvent
    data class ConfirmationRequested(val actionId: String) : ButlerEvent
    data class ActionExecuted(val actionId: String) : ButlerEvent
    data class ActionUndone(val actionId: String) : ButlerEvent
    data class ProactiveRunFinished(val runId: String, val decision: String) : ButlerEvent
    data class Error(val requestId: String?, val message: String) : ButlerEvent
}
```

### 6.2 插件能力

```kotlin
interface ButlerPlugin {
    val id: String
    val version: String
    val capabilities: Set<ButlerCapability>

    suspend fun onStart(context: ButlerPluginContext)
    suspend fun onEvent(event: ButlerEvent, context: ButlerPluginContext)
    suspend fun onStop()
}
```

首批插件不超过七个：

1. `fish-expression`：根据真实状态展示鱼；
2. `fish-game`：独立的喂养、装扮、收集和成长；
3. `memory`：记忆写入、衰减、召回和审计；
4. `proactive`：主动候选、安静时段、预算和静默；
5. `time-actions`：时间 Agent 的强类型动作；
6. `briefing`：日报、周报和复盘；
7. `approval`：确认、拒绝、撤销和权限记录。

健康、支付通知、跨应用采集等能力以后单独增加，不能因为插件化就默认拥有权限。

## 7. 管家 Agent 的执行链

```text
用户语音/文字
      |
      v
FishButler Persona
      |
      v
本地解析 / 云端理解
      |
      v
结构化意图
      |
      v
时间事实查询与规则校验
      |
      +--> 直接回答
      |
      +--> 生成预览并等待确认
      |
      +--> 执行可逆动作
      |
      +--> 生成主动候选
      |
      v
Room + 操作历史 + ButlerEvent
      |
      v
胖鱼状态与表达
```

这里的关键变化是：管家 Agent 不再只是 `DeepSeekClient().interpret()` 的一次性请求，而是一个由事件、记忆、主动控制、工具和表达组成的长期运行对象。

## 8. DSH 迁移策略

### 阶段 A：只研究 DSH 和 Pi

暂时不引入 DSH 依赖，完成：

- 事件模型对照；
- 插件边界整理；
- 工具审批对照；
- 记忆和主动唤醒参数对照；
- Pi 的会话、工具和状态实现分析。

### 阶段 B：实现 Android 原生 Butler Kernel

先在时间 Agent 中实现：

- `ButlerEventBus`；
- `ButlerState`；
- `ButlerPluginRegistry`；
- `ButlerToolRouter`；
- `FishButler`；
- 一个不写数据库的原创鱼占位表达层。

此阶段不增加 Room 表，先验证架构和状态链。

### 阶段 C：接入记忆和主动能力

再增加：

- Room `v12`；
- 三层记忆；
- 事实键和置信度；
- 召回审计；
- 主动预算；
- 安静时段；
- 静默收尾；
- 复盘和用户纠正。

### 阶段 D：评估是否需要 DSH 兼容层

只有当出现以下需求，才考虑兼容层：

- 需要运行大量现有 DSH JavaScript 插件；
- 需要快速接入 DSH 生态中的多个成熟插件；
- Android 原生插件无法满足扩展速度；
- 已经有可靠的脚本沙箱、权限隔离和版本管理。

即使进入阶段 D，也优先做：

```text
时间 Agent 原生 Butler Kernel
        |
        v
受限 DSH Plugin Adapter
        |
        v
少量经过审核的插件
```

不要让 DSH Host 取代时间 Agent 的核心事实和权限系统。

## 9. 最终判断

你的目标下，答案不是“Pi 和时间 Agent 互相调用”，而是：

```text
时间 Agent 内部 = 一个真正的 Fish Butler Agent
大肥鱼 = Agent 的人格和工作状态表达
养鱼游戏 = 独立的娱乐系统
DSH = 插件化 Agent 的参考架构
Pi Mobile = 研究 Agent 工具循环、状态和审批的样本
```

是否嵌入 DSH：

- **完整嵌入 DSH：现在不要。**
- **借鉴 DSH 插件思想：应该。**
- **实现自己的轻量 DSH-like Butler Kernel：应该。**
- **未来运行少量 DSH 插件：可以作为后续兼容层评估。**

最先应该开发的不是“把 DSH 打进 APK”，而是：

1. `FishButler` 长期管家对象；
2. `ButlerEventBus`；
3. `ButlerState`；
4. `ButlerToolRouter`；
5. `fish-expression` 插件；
6. `fish-game` 独立游戏状态；
7. 让真实的解析、写入、确认、提醒和错误都驱动大肥鱼工作状态。

做到这一步后，用户感受到的才是“我在时间 Agent 里养了一条会工作的鱼”，而不是“时间 Agent 旁边多了一个动画”。

## 10. 证据与边界

- Pi Mobile 当前已核实为独立的内嵌 Agent 工作台，现有资料和源码位于 `独立手机 Pi 工作区（未纳入本仓库）`。
- 时间 Agent 当前已有本地解析、云端结构化 action、预览、确认、执行、撤销和提醒能力。
- 之前的“Pi 外置协作者”方案与本目标不一致，本文件以本目标为准。
- 本轮未修改时间 Agent 产品源码，也未把 DSH 或 Pi 运行时加入 APK。
