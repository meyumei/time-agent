# 第十轮：健康数据同步与无限时间轴（0.6.0）

日期：2026-10-24。本轮响应两条新方向：时间轴按自然时间无限延伸、去掉学期概念；把运动健康类应用的睡眠与健身记录自动同步为本应用的实际记录（第一优先级）。

## 需求

### R1001 无限时间轴（去学期化）

时间轴、复盘与导航永远只按自然日/周/月表达，不出现"学期/教学周"边界或提示：

- 时间轴页眉与工具栏副标题只显示年份与今天的日期，不再显示"XX学期 · 第N教学周"。
- 课程详情不再显示教学周；课程在时间轴上就是落在具体日期时间上的条目。
- `academic_terms` 与教学周换算仅保留在课表导入流程内部（把课表展开为具体日期实例的参数），不是导航或统计的边界。
- 统计口径不变：复盘仍按自然周窗口计算。

### R1002 睡眠自动同步（第一优先级）

通过 **Health Connect**（安卓官方健康数据中枢）读取 `SleepSessionRecord`，写入 `time_records`：

- 来源 App 无关：小米运动健康、华为运动健康、Keep、训记等任何写入 Health Connect 的应用都自动覆盖。
- 记录形态：title=睡眠，source=HEALTH_SYNC，分类取"睡觉"活动模板的分类（缺失则未分类）；跨午夜保持一条记录（时间轴已有跨日拆分显示）。
- 去重：以 Health Connect 记录 id（uid）为外部键，复用课程导入 externalKey 模式；重复同步不产生重复记录。

### R1003 健身记录自动同步（第一优先级）

读取 `ExerciseSessionRecord`：title 优先用记录自带标题（如训记训练名），否则按运动类型映射中文（力量训练/跑步/步行/骑行/游泳/瑜伽等，缺省"健身"）；分类取"健身"活动模板。

### R1004 同步规则（数据安全）

- 手工保护：同步写入的记录被用户手工修改（isManuallyEdited）后，来源后续变化不再覆盖，仅刷新同步时间。
- 删除墓碑：用户删除同步记录后不再自动恢复（health_sync_items.userDeleted）；若因撤销恢复重新出现则自动修复关联。
- 进行中会话（结束时间为未来）跳过，待结束后同步。
- 同步写入不进操作历史、不清除重做分支：自动数据不应污染撤销/重做链。
- 同步范围可配：7/14/30 天，默认 14 天；手动"立即同步"随时可用。
- 开启"自动同步"后，每次打开应用在数据加载完成后静默同步一次（失败不打扰）。

### R1005 设置页

"我的 → 健康数据同步"：Health Connect 状态（不可用/需授权/已就绪，含授权入口）、自动同步开关、睡眠/健身分项开关、同步范围、立即同步与结果（新增/更新/手工保护/无变化计数）、最近同步时间、已同步条目列表（标题、时间、来源应用、状态）。

## 非目标（本轮不做）

- 事件驱动建议引擎、日汇总两段式（第十一轮）。
- 后台定时同步（WorkManager）、Health Connect 写入、心率/步数等非时段型指标。
- 训记云 API 直连：若训记未接入 Health Connect，先在真机验收确认；未接入前其数据不自动同步，不伪造。

## 技术方案

- Room v5 新增 `health_sync_items`（uid 主键、kind、originPackage、recordId 外键 SET_NULL、userDeleted、lastSyncedAt）；`time_records` 无结构变化，source 新值 `HEALTH_SYNC`。
- `HealthDataReader` 接口抽象"状态 + 读睡眠 + 读训练"；真实实现 `HealthConnectReader`（connect-client 1.1.0），测试用假读取器。
- 同步事务在 `TimeRepository.syncHealthSamples`：单事务内完成查重、插入、跟随来源更新、保护与墓碑，记录 id 采用 `health:<kind>:<uid>` 确定性命名保证幂等。
- 权限：manifest 声明 `health.READ_SLEEP`/`health.READ_EXERCISE` 与权限说明入口（API 34+ activity-alias；低版本 intent-filter），运行时用 `PermissionController.createRequestPermissionResultContract()` 申请。
- 隐私：数据只在本机读取与存储；不同步任何数据到云端；DeepSeek 上下文不包含健康记录明细。

## 验收口径

- 自动测试：同步引擎（新增/幂等/跟随更新/手工保护/删除墓碑/撤销修复/进行中跳过/分项开关）、迁移 4→5 历史数据保留、设置页 UI 流程（状态展示、授权提示、立即同步结果、条目列表）。
- 构建产物 `:app:assembleDebug` + Lint 0 错误，APK 与既有版本同证书。
- 真机待验收（本轮不连手机，交付本地 APK）：澎湃 OS 上 Health Connect 可用性、小米运动健康睡眠写入后同步结果、训记是否出现在 Health Connect 数据源列表、自动同步时机。

## 真机排查记录（2026-10-24 晚，K70 Ultra / Android 16 / 小米运动健康 3.59.1）

用户现象：已开权限、点"立即同步"仍无数据。逐层排查结论：

1. **时间 Agent 读链路正常**：READ_SLEEP/READ_EXERCISE 均 granted=true；Health Connect"近期数据访问情况"记录了时间 Agent 22:20/22:22/22:23 三次读取；同步返回"新增 0"说明读取成功但 HC 内为 0 条。
2. **根因在写入侧**：小米运动健康对 HC 的全部写入权限（WRITE_SLEEP/WRITE_EXERCISE 等 11 项）原本都是 granted=false——用户开的是时间 Agent 的读取权限，小米从来没被允许写入。已处理：`pm grant` 授予 WRITE_SLEEP/WRITE_EXERCISE，并在 HC"应用权限 → 小米运动健康"开启"全部允许"（步数/锻炼/路线/距离/爬升/睡眠全开）。
3. **导出是事件驱动的**（逆向源码证据 `source-k70-mi-health-3.59.1`）：`HealthConnectDataSyncedReceiver` 监听小米内部广播 `fitness.action.SUMMARY_SYNCED`/`reason_data_changed`/`recent_data_changed_broadcast` → 按类型经 `HealthConnectSyncUtils` 检查写入权限 → `SleepSyncBiz`/`StepSyncBiz`/`SportSyncBiz` 等增量导出（`HealthConnectSyncDao` 游标）。写入类型含 SleepSessionRecord/ExerciseSessionRecord，与时间 Agent 读取类型完全匹配。授权发生在今天睡眠汇总之后，尚无事件触发，故 HC 暂为空——**明晨睡眠汇总完成即会导出，届时打开时间 Agent 自动同步**。
4. **训记未接入 Health Connect**（真机 HC 应用列表中不存在 com.trainnote.rn），其训练数据现阶段无法经 HC 自动同步；替代通道（导入文件/URL Scheme/云 API）留待后续轮次评估。
5. 手动添加临时运动的验证被中断，未产生测试数据；小米运动健康的升级提示按约定点"暂不"，未升级。

待用户明晨验证：起床后打开时间 Agent（或"立即同步"），睡眠应出现为"睡眠"实际记录；若当天想立即验证，可在小米运动健康完成一次"手动添加运动"，约一分钟后同步。

### Gadgetbridge 通道（2026-10-25 补充）

用户询问 GB 是否可作为数据源：**可以且已配置**。GB 0.95.1（code 255）声明全部 24 项 Health Connect 写入权限并支持历史回填（3/7/30 天/全部/自定义日期）；华为 WATCH GT 2-9D4 在 GB 内已配对连接，仪表板有真实睡眠分段数据。已在其"设置 → 外部集成 → Health Connect"开启导出、选定该设备，系统授权页通过（WRITE_SLEEP/WRITE_EXERCISE 等 granted=true）。剩余一步（用户手动）：在该页"同步状态"区触发初始回填。训记仍未接入 Health Connect。

### GB 与华为运动健康睡眠时长不一致的原因（2026-10-25 真机实测对照）

同一晚（10月24日夜→25日晨）两 App 实读数据：

| 项 | 华为运动健康 | Gadgetbridge |
|---|---|---|
| 总时长 | **6 小时 35 分钟**（得分 84） | **约 5 小时 0 分**（图表值 5h1min） |
| 睡眠区间 | ≈01:51–08:26 连续一窗（含微觉醒） | **两段：01:44–04:22、06:04–08:25**，中段 04:22–06:04 不计入 |
| 分期 | 深 2h19m · 浅 3h9m · REM 1h7m · 清醒 3 次 | 深睡 0s，几乎全部记为浅睡 |

结论：**差值 ≈1.5 小时，主因是 GB 只累计连续睡眠段、把夜间间断（04:22–06:04）排除，而华为把整个在床窗口算作"夜间睡眠"**；次因是分期解析——GB 对 GT 2 的深睡/REM 解析基本失效（深睡 0s），华为三期齐全。这与两 App 的实现一致（华为端侧私有引擎 libDetailSleepJni；GB 开源启发式）。

对时间 Agent 的实际影响：若 GB 先入库，去重后当晚记录为 GB 的 ~5h，会触发"睡眠不足"建议；若小米/华为口径先入库（6h35m）则不会。**睡眠来源优先级设置（第十二轮）因此更有必要**，且"睡眠不足"规则阈值需按来源口径考虑容差。
